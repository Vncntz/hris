# TASK-0023 — Secure first-administrator provisioning

Status: PLANNED — planning only; implementation requires a separate explicit operator instruction after this planning PR and its exact-merge-SHA push CI pass.

Parent implementation item: [IMP-013](../implementation/tasks/IMP-013.md)

## Goal and scope

Provide an explicit, once-only, offline-capable way for an installation operator to create the first administrator with an operator-chosen password. A freshly migrated database must remain unusable for login until this command succeeds. No default or vendor-known credential may exist.

Identity & Access owns provisioning, account/role/permission state, password validation and hashing, and the durable bootstrap invariant. `hris-app` owns only the local command adapter and application composition. Platform/Operations supplies the existing append-only audit contract through `shared-kernel`; do not expose its persistence or reverse module dependencies.

This work order plans the next focused IMP-013 slice. This planning PR changes documentation only and does not create a command, schema, configuration, dependency, or runtime behavior.

## Acceptance criteria

1. Provisioning is available only through an explicitly invoked local operator command using the existing single deployable application. The provisioning process must not start an HTTP listener or Vaadin setup route. Ordinary application startup cannot provision an account, and anonymous web callers cannot invoke the bootstrap service. Local OS/process and database access are the operator trust boundary; document that possession of this access is privileged. Do not introduce an external identity service or a second deployable application.

2. The command reads the chosen login and a twice-entered password through an interactive console with password echo disabled. Fail closed if secure console input is unavailable. Never accept passwords through command-line arguments, environment variables, configuration files, URL/query/form parameters, stdin redirection, or checked-in defaults. Cancellation or mismatched confirmation causes no persistent mutation. Clear mutable password buffers on every exit path; keep unavoidable encoder copies short-lived and exclude credentials from printable request/result objects and exceptions.

3. Reuse existing canonical-login rules and adaptive Argon2id encoding. Enforce the D-151 default minimum of 12 characters, allow longer passwords, define and test a bounded maximum compatible with the encoder, and reject over-limit input without truncation. Do not trim, case-fold, or otherwise silently transform passwords. This slice must not claim production hardware calibration or full password-policy qualification; record that later hardening obligation.

4. A durable, database-enforced once-only bootstrap state serializes competing provisioning commands in a short READ COMMITTED transaction. Empty-table counts alone cannot protect concurrency. The account, enabled administrator role, explicit permission assignment, completion marker, and successful audit evidence commit atomically. After successful completion, restart, account disablement/deletion, role disablement, or assignment removal must never reopen bootstrap. Existing account or authorization data without a completed bootstrap marker must fail closed for manual reconciliation; do not adopt, overwrite, or elevate an existing principal. No reset/recovery backdoor is included.

5. Create exactly one enabled account with an independently generated stable public UUID, an operator-chosen canonical login, and only its adaptive password hash. Create an enabled `administrator` role and the single narrowly scoped `identity:admin` authority, assigning both only during explicit successful provisioning. No wildcard, superuser bypass, complete future-module permission catalog, or implicit privilege from the role name is allowed. Future administration must explicitly enforce this authority and its own audit/re-authentication requirements; this task exposes no such administration API. Failed provisioning cannot leave a partial account, role, permission, membership, or completed marker.

6. Successful provisioning appends `FIRST_ADMINISTRATOR_PROVISIONED` through the existing `AuditRecorder` in the same transaction. Use the newly created account public UUID as actor and target and a fixed non-secret context identifying the local bootstrap origin; this is an explicit bootstrap exception to an already-authenticated actor, not a caller-supplied actor override for ordinary services. Do not persist the login, password, hash, secret input, or serialized request in audit context. Audit failure rolls back all provisioning state. Rejected/repeated attempts return bounded non-secret failure information and do not forge a successful audit event.

7. A newly provisioned account authenticates through the existing normal provider, receives exactly the intended authority, and passes `CurrentActor.requireAuthority("identity:admin")`. Authentication without assignments still grants none. Existing disabled-account, lockout, bad-credentials, authority-filtering, session, CSRF, and architecture regressions remain intact. Bootstrap does not log in automatically or create a credential-bearing principal/session.

8. Add focused tests for input validation, canonical names, password length/confirmation/secret handling, command opt-in and no-console refusal, repeat attempts, fail-closed legacy state, rollback, and absence of an anonymous setup route. Real-MySQL tests must prove pristine migration with no usable account/authorization seed, V5 upgrade preserving existing data without elevation, successful provision-and-authenticate behavior, durable closure across restart and account/assignment changes, atomic audit failure rollback, and concurrent competing commands producing exactly one committed administrator and success audit event. Use deterministic synchronization for contention, not timing-only sleeps; unexpected skips are failures.

9. Update mutable module, migration, operator runbook, TASK, IMP, and implementation-state documentation with verified behavior and actual commands. The runbook must explain privileged local invocation, secure console availability on supported Windows/Ubuntu environments, first-use closure, non-secret failure handling, and the absence of a recovery/reset path. Examples must contain no credential literal or customer data. All local, exact-head CI, protected integration, and exact-merge-SHA push checks pass before TASK-0023 becomes complete.

## Security, privacy, and non-goals

Use synthetic, ephemeral test input only; never commit reusable credential literals, customer data, hashes, MFA secrets, or recovery codes. Tests may generate ephemeral passwords in memory but must not print or retain them in reports/artifacts. Do not request production credentials in AI context. Do not add a User/Worker coupling or allow another module to own security state.

Normal account creation/change/reset, enable/disable administration, role/permission assignment management, Vaadin administration screens, Agency mutation authorization, TOTP enrollment/challenge/recovery, privileged re-authentication, session revocation, business-module permission enforcement, SSO/LDAP/OIDC, cloud dependencies, and generalized policy engines are out of scope. Bootstrap must not become an alternate login, permanent privileged mutation channel, or recovery mechanism.
