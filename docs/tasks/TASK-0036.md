## Scope and acceptance criteria

1. Client Management exclusively owns the new Client Company and Client Site JPA entities, repositories, mutations, and persistence mappings.

2. Both Client Company and Client Site have stable public UUIDs distinct from internal relational primary keys. Internal IDs must never cross the module's public application/query boundary.

3. Client Site belongs to exactly one Client Company. The database must enforce the relationship with deliberate referential integrity; normal application behavior must not physically delete either aggregate.

4. This task intentionally models only minimal master information required for the foundation: a bounded nonblank display name plus lifecycle/reference state. Do not invent contact-person, payroll, billing, assignment, statutory, recruitment, or other unrelated fields.

5. Display name is descriptive data, not entity identity. Do not impose an unapproved business rule that legal/display names must be globally unique. Stable public UUID is the cross-module identity.

6. Provide authenticated commands to create a Client Company and create a Client Site under an existing Client Company. Newly created records are active.

7. Provide explicit rename/update-display-name commands for Company and Site so corrections do not require replacement records.

8. Provide explicit activate/deactivate commands for Company and Site. No hard-delete administration API is introduced.

9. Company deactivation preserves its Sites and all stable identities. An inactive Company makes its Sites unusable for new active business references without rewriting each Site's own lifecycle state.

10. Site activation must reject an inactive parent Company. Reactivating a Company does not silently activate Sites whose own stored state is inactive.

11. Missing targets, invalid names, lifecycle no-ops, inactive-parent violations, stale/concurrent mutations, persistence failures, and audit failures return bounded application outcomes without SQL, internal IDs, stack causes, credentials, session IDs, or arbitrary request payloads.

12. Define the Client Management administrative authority as the stable application authority key `client:admin`.

13. Every mutation must first require `CurrentActor.requireAuthority("client:admin")` and derive its audit actor only from `CurrentActor.requireUserId()`.

14. Do not seed `client:admin`, Roles, memberships, or any authorization assignment in a migration. Existing Identity & Access administration remains responsible for creating/assigning persisted permission definitions.

15. Expose a narrow immutable Client Management reference/query contract suitable for later IMP-015/IMP-020 use. It must allow resolution of Company/Site stable identities, their parent relationship, display names, and active/effective-active state without exposing entities, repositories, lazy JPA state, or internal IDs.

16. Cross-module consumers may read through that explicit contract but may not write Client Management-owned aggregates.

17. Each successful administrative mutation records exactly one append-only privacy-minimized audit event in the same database transaction as the mutation. Actor is the authenticated Account public UUID; target is the affected Company/Site public UUID.

18. Audit actions must distinguish Company creation/name/lifecycle and Site creation/name/lifecycle. Context may include the stable parent Company UUID where needed, but must not contain arbitrary serialized requests or unrelated data.

19. Mutation and audit must flush/commit atomically. Audit or persistence failure rolls back the business mutation.

20. Use short explicit transactions and deterministic locking/version behavior sufficient to prevent silent lost updates. Concurrent lifecycle/name mutations must produce a valid serialized outcome or a bounded stale/conflict rejection.

21. Allocate the actual next global forward Flyway version after refreshing `main`. On the reviewed baseline the expected migration is `V10__add_client_company_and_site.sql`.

22. The migration must create only the Client Company/Site schema and necessary keys, indexes and constraints. It must not seed customer records or alter Identity, Agency, audit, or unrelated business data.

23. Released V1-V9 migrations are immutable. Verify clean-schema creation and populated V9-to-new-version upgrade equivalence on real MySQL.

24. Add/update the Client Management module documentation and migration index with durable architecture and operational facts only.

25. Preserve the existing modular-monolith architecture, single deployable application, offline-capable core, MySQL/JPA stack, Identity behavior, audit foundation, and all existing tests.

This task does not implement Manpower Request / Job Requisition, recruitment, Worker/Employment, Position/Deployment, Assignment Terms, addresses/contact-person master data, client-specific compensation or billing, scheduling, attendance, Client Portal behavior, generalized authorization administration, or a broad Vaadin Client Management UI.

## Security, privacy, and audit

Treat Company/Site data as installation business data and minimize collection in this slice.

Authorization must be enforced in the Client Management application-service mutation boundary, not only in a future UI.

No credentials, MFA data, hashes, session identifiers, infrastructure exception details, or real customer data may appear in source, fixtures, audit context, logs, CI output, or AI context.

Use generated synthetic Client Company/Site values in tests.
