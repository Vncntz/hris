# TASK-0018 — Harden Agency initialization under contention

Status: POST_MERGE_VERIFIED; implementation complete. IMP-012 closure review remains pending.

## Goal

Make simultaneous Agency initialization reliable when MySQL reports a transient deadlock or lock contention. Preserve the database singleton invariant and the application-level `Agency configuration is already initialized` contract when another caller wins. Keep the successful Agency creation and its audit event atomic.

## Observed baseline and authority

PR #30's local verification recorded an intermittent MySQL deadlock in the unchanged simultaneous-initialization test. An unchanged Agency-only rerun and the final full MySQL run passed. The production path in `AgencyConfigurationService.initialize` checks for an existing singleton row, then saves and flushes a new row in a `READ_COMMITTED` transaction. It translates a data-integrity failure into the duplicate contract. A transient deadlock can abort that transaction before a winner is known; a duplicate response must therefore be based on an actual committed Agency, not merely on the transient error. The real-MySQL concurrency test currently expects one successful Agency, one clean duplicate response, and one success audit.

The [frozen planning index](../planning/INDEX.md) identifies D-081 (one Agency root), D-109/D-110 (module boundary), D-111 (normal JPA persistence), D-112 (short transactions and bounded transient retry), D-132 (no customer production data), and D-147/D-148 (verification and completion). No approved ADR changes this direction. [TASK-0016](TASK-0016.md) established the root and database constraint; TASK-0017 corrected the no-seed test ordering. IMP-012 remains active for this contention outcome. IMP-013 has not begun.

## Implementation direction

1. Inspect the current service, entity, repository, unit and real-MySQL tests, V4, and relevant module/app POMs before choosing the smallest implementation.
2. Preserve the database-enforced singleton and the existing application-level duplicate message. Handle only recognized transient deadlock/lock-contention failures with a small bounded attempt in a **fresh transaction after the aborted transaction**. Do not retry arbitrary non-transient database errors or claim that a duplicate exists until an Agency actually won and committed.
3. Preserve atomic Agency creation and `AGENCY_CONFIGURATION_INITIALIZED` audit recording, including the existing surrounding-transaction rollback behavior. A losing or rolled-back attempt must leave no success audit evidence. Preserve explicit actor, public ID, and UTC conventions.
4. Add deterministic automated coverage that injects or simulates the transient-contention path and verifies fresh-transaction behavior, bounded handling, true-winner detection, and no false duplicate. Do not make correctness depend on probabilistically reproducing a deadlock.
5. Retain real-MySQL simultaneous-initialization coverage proving one Agency commits, a competing caller loses cleanly, one initialization success audit commits, and no second root appears. Preserve TASK-0017's no-seed ordering and after-test cleanup semantics.
6. Keep changes in Platform Operations, its tests, and only necessary app integration coverage and mutable documentation. Do not introduce Redis, distributed locking, Spring Retry, another service or deployable, or a new dependency unless existing Spring transaction/data-access facilities are demonstrably insufficient.

## Acceptance criteria

1. The planning predecessor gate above is independently verified before implementation.
2. Concurrent initialization preserves the single-Agency database invariant and the existing duplicate contract when another caller has committed.
3. A transient deadlock/lock-contention abort is handled with a bounded fresh-transaction attempt. Non-transient failures propagate accurately; no false duplicate is reported when no Agency has committed.
4. The successful Agency and its initialization audit commit together. A surrounding rollback still removes both; losing and rolled-back attempts leave no success audit.
5. Deterministic tests cover the transient path, bounded outcome, and winner/no-winner distinctions. Real-MySQL simultaneous-initialization coverage proves one committed Agency, one clean loser, exactly one success audit, and no second root.
