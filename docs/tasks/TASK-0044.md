The ownership correction enforces selected-Company ownership for all Site state:
When the selected Company public UUID changes, Site rows, Site selection, Site paging/action state and any other state derived from the previous Company become non-actionable before relying on the new Company's Site query result. If the new Site query fails, the Site area remains in a safe terminal error state and does not continue presenting previous-Company rows as belonging to the current Company.

`ClientSiteReference.companyPublicId()` is the authoritative parent identity available to the UI. Site selection fails closed unless a selected Site's `companyPublicId()` equals the current selected Company's `publicId()`. A stale or mismatched Site is cleared/rejected, cannot enable rename/lifecycle controls and cannot reach `renameSite`, `activateSite`, `deactivateSite` or another Site mutation.

The ownership check is enforced at the Site selection and mutation boundaries so correctness does not depend solely on grid rendering or on a prior selection callback. Backend authorization and lifecycle enforcement remain authoritative.

Preserves the bounded/non-recursive Company/Site load-failure behavior without query recursion, automatic unbounded retry or fabricated Site state.

## Goal

Implement a responsive, accessible Vaadin administration experience for Client Companies and their Client Sites using the already-integrated Client Management query, mutation and exact-authority security contracts.

Provide administrators holding exact `client:admin` authority with a discoverable `/clients` workspace for bounded Company/Site browsing, selection, creation, renaming and activation/deactivation while preserving all backend ownership, authorization, lifecycle, audit and concurrency semantics.

## Scope

Add an authenticated Client administration route at `/clients`, using `MainLayout`, `@Menu`, an appropriate page title and the TASK-0042-supported exact authority mechanism, preferably `@RolesAllowed(ClientManagementService.ADMIN_AUTHORITY)`.

The route must appear through the existing access-filtered menu only for users permitted to open it. Menu hiding is supplementary; direct route access must be denied server-side to authenticated users without `client:admin`, and anonymous access must retain the existing login flow.

Browse Client data only through:

- `ClientAdministrationQueries.companies(offset, limit)`;
- `ClientAdministrationQueries.sites(companyPublicId, offset, limit)`.

Use bounded offset paging and the returned `hasMore` flag. Maintain only bounded page rows, public identities, edit versions and small UI state in the Vaadin session. Do not request or fabricate a total count. Do not expose an unbounded page size, load complete Company/Site collections, or implement unsupported generalized search/filter/sorting infrastructure.

Display records in the backend's authoritative ordering: display name ascending under database collation with public UUID as the stable tie-breaker. UI controls must not imply unsupported cross-page sorting or filtering.

The Company area must support:

- bounded browsing and page navigation;
- selection of one Company;
- create;
- rename using the current edit version;
- activate;
- deactivate;
- clear active/inactive status.

The Site area must operate only for the selected Company and support:

- bounded Sites-by-Company browsing;
- create;
- rename using the current edit version;
- activate;
- deactivate;
- clear presentation of both stored Site active state and effective active state.

A Site whose stored state is active while its Company is inactive must be represented as stored-active but effectively inactive. Company deactivation must not visually imply that individual Site stored states were changed.

Create or activate Site controls should be disabled with an understandable explanation when the selected Company is inactive, while backend enforcement remains authoritative. Operations that remain valid under an inactive Company, such as Site rename or deactivation, must not be incorrectly disabled.

Mutate only through `ClientManagementService`:

- `createCompany`;
- `renameCompany`;
- `activateCompany`;
- `deactivateCompany`;
- `createSite`;
- `renameSite`;
- `activateSite`;
- `deactivateSite`.

After every successful mutation, refresh the affected bounded Company/Site data from `ClientAdministrationQueries` so subsequent edits use current committed edit versions and lifecycle state. Refresh Sites whenever Company activation state changes because Site effective activity depends on the parent state.

Duplicate display names are valid. Never deduplicate, key, select or mutate records by display name; public UUID identity must remain distinct internally.

Use focused dialogs/forms for create and rename. Mirror safe client-side validation such as required trimmed names and the 200-character limit for usability, while treating `ClientManagementService` as the authoritative validation boundary.

Lifecycle actions require explicit confirmation. Company deactivation confirmation must explain that its Sites become effectively inactive without changing their stored Site states. Prevent accidental duplicate form or lifecycle submissions.

Map `ClientManagementException.Reason` to bounded user-facing behavior without displaying exception text or infrastructure details:

- `INVALID_NAME`: inline/safe name validation feedback;
- `INVALID_TARGET` or `NOT_FOUND`: explain that the selected record is no longer available, clear stale selection where appropriate and refresh;
- `INVALID_PAGE`: recover to a valid bounded page and show safe load feedback;
- `NO_CHANGE`: explain that there is no change to save without retrying the mutation;
- `INACTIVE_COMPANY`: explain that the Company must be active for the requested Site action, then refresh affected state;
- `STALE_VERSION`: report a concurrent change, refresh the affected Company/Site page and require the administrator to review current data before retrying;
- `CONFLICT`: provide generic concurrent-operation/retry feedback and refresh;
- `PERSISTENCE_FAILED`: provide a generic retryable failure without SQL, exception, stack-trace or infrastructure detail.

### Correction scope boundaries

TASK-0044 correction work must eliminate synchronous recursive retry when a Company or Site query/load fails.

Load failures and mutation-result refresh behavior must be treated as distinct paths. A failed query/refresh must terminate in a stable, intentional safe UI error state rather than routing through a generic handler that immediately invokes the same load again.

`PERSISTENCE_FAILED` during Company or Site loading must not synchronously retry the same query. Unexpected load failures must likewise fail safely without recursive re-entry.

`INVALID_PAGE` may perform only a bounded recovery to a valid page, such as resetting to offset zero. If that recovery load also fails, surface safe feedback and stop rather than recursively retrying.

Mutation outcomes that require refreshing current committed state—such as `STALE_VERSION`, `CONFLICT`, `NOT_FOUND`, `INVALID_TARGET`, or `INACTIVE_COMPANY` where already required by this TASK—may still initiate the appropriate bounded refresh. If that refresh itself fails, the load-failure path must stop safely.

No error path may expose raw exception messages, SQL/database details, causes, stack traces, infrastructure information, or sensitive data.

## Contract context

`ClientManagementService.ADMIN_AUTHORITY` is exactly `client:admin`.

Client Management commands already enforce `client:admin`, derive the authenticated actor, own transaction/locking/version semantics and append exactly one audit event for each successful mutation.

Company/Site names are trimmed, nonblank, bounded to 200 Java string units and allow duplicates. Public UUIDs, not names or relational IDs, determine identity.

Creation produces active records. Site creation and Site activation reject an inactive Company. Company deactivation preserves Sites and their stored activity. Company reactivation does not activate Sites whose stored state is inactive.

There is no hard-delete command.

TASK-0042 configured Vaadin/Spring Security to use persisted authorities without a `ROLE_` prefix and proves exact `@RolesAllowed("client:admin")` menu/direct-navigation behavior.

TASK-0040 supplies `MainLayout`, access-filtered `MenuConfiguration` navigation, responsive shell and existing logout behavior.

TASK-0041 owns `/login` presentation and authentication behavior. Preserve it unchanged.

## Acceptance criteria

1. `/clients` is an authenticated `MainLayout` route, is discoverable through the existing access-filtered menu for exact `client:admin`, and is denied server-side for authenticated users lacking that exact authority. Anonymous direct access retains the existing login behavior.

2. Company and Site data are obtained only through `ClientAdministrationQueries`. No Client Management entity, repository, JPA query or relational ID is accessed from `hris-app`.

3. Company and Site browsing is bounded. Paging uses finite limits and `hasMore`, supports Previous/Next or equivalent bounded navigation, and never fabricates or queries a total count.

4. The UI preserves the backend's deterministic ordering and does not advertise unsupported generalized search/filter/sorting behavior.

5. Duplicate Company and Site names render as separate records and all selection/mutation state is bound to public UUID identity, never display name.

6. Company creation, rename, activation and deactivation call only the corresponding `ClientManagementService` commands and refresh affected query data after success.

7. Site creation, rename, activation and deactivation call only the corresponding `ClientManagementService` commands for the currently selected Company and refresh affected query data after success. A Site whose `companyPublicId()` does not equal the current selected Company's `publicId()` is stale/mismatched UI state: it must fail closed, must not enable Site mutation controls and must produce zero Site mutation service calls.

8. Company active state, Site stored active state and Site effective active state are unambiguous. An active Site under an inactive Company is presented as stored-active/effectively-inactive rather than as if its stored state changed.

9. Site creation/activation is visibly unavailable while the selected Company is inactive, without weakening backend authorization or lifecycle enforcement.

10. Forms provide accessible validation and safe feedback. Invalid, missing, stale, conflict, inactive-parent and persistence outcomes are mapped from fixed `ClientManagementException.Reason` values without exposing raw exception messages or infrastructure details.

11. `STALE_VERSION` is treated as a concurrent-change condition: no success is shown, affected data is refreshed, and the administrator must review current state before retrying.

12. Lifecycle actions require confirmation; Company deactivation communicates its effective-state impact on Sites. Accidental duplicate submissions are prevented.

13. Empty/no-selection/error/disabled/paging-boundary states are intentional and understandable. Changing Company context invalidates Site state belonging to the previous Company before it can be acted upon. If the new Company's Site query fails, no previous-Company Site row may remain actionable as though it belonged to the current Company. A failed query or mutation never leaves the page presenting an unverified successful or wrong-parent state.

14. Desktop/laptop and narrow layouts remain usable without horizontal page overflow, clipped dialogs/actions or loss of access to Company/Site controls.

15. Keyboard navigation, dialog focus, visible focus indicators, accessible labels/semantics and non-color-only lifecycle status are verified. Do not add a second page-level H1 under the MainLayout-owned heading.

16. Existing `/login`, shell, logout, TASK-0042 authority behavior and unrelated routes remain unchanged.

17. No backend/domain/persistence/security behavior, Client Management implementation, migration, permission definition, assignment or audit behavior is modified.

18. Persistent Company query/load failure cannot recursively invoke `ClientAdministrationQueries.companies(...)`. The failed load produces bounded safe user-facing feedback and stable control/paging state. Deterministic tests prove the query count is bounded for the failed load.

19. Persistent Site query/load failure cannot recursively invoke `ClientAdministrationQueries.sites(...)`. The failed load produces bounded safe user-facing feedback and stable control/paging state. When the failure follows a Company context change, Site rows/selections/actions from the previous Company are cleared or otherwise made non-actionable. Deterministic tests prove both the bounded query count and zero wrong-parent Site mutation calls.

20. A mutation-triggered refresh that subsequently encounters a load failure terminates through the load-error path; mutation refresh handling must not recreate the recursive query cycle.

21. Browser verification must exercise the actual rendered Vaadin workflow rather than merely inspecting source text, annotations, component metadata, or static DOM presence. ## Implementation and verification notes

### Implementation summary

1. **Route & Shell Authorization**:
   - `ClientAdministrationView` registered at `/clients` with `layout = MainLayout.class`.
   - Annotated with `@RolesAllowed(ClientManagementService.ADMIN_AUTHORITY)` (`client:admin`), `@PageTitle("Clients")`, `@Menu(order = 10, icon = "vaadin:building", title = "Clients")`, `@StyleSheet("hris/clients.css")`.
   - Side navigation visibility is access-filtered via `MainLayout` / `MenuConfiguration`. Direct route access is enforced server-side.
   - Preserves single H1 heading rule (`MainLayout` owns H1; view uses semantic H2 headings for "Companies" and "Sites").

2. **Data Access & Boundary Rules**:
   - Reads strictly through `ClientAdministrationQueries` (`companies(offset, limit)`, `sites(companyId, offset, limit)`).
   - Mutates strictly through `ClientManagementService` commands (`createCompany`, `renameCompany`, `activateCompany`, `deactivateCompany`, `createSite`, `renameSite`, `activateSite`, `deactivateSite`).
   - Zero direct JPA entity/repository/persistence access; no backend/domain/security contracts modified.

3. **Responsive Master-Detail UI**:
   - Dual-section administration workspace with accessible semantic `<section>` and ARIA labels.
   - Bounded pagination (15 items per page) without fabricated total counts, supporting Previous/Next navigation and boundary disablement.
   - Preserves selection across programmatic grid refreshes using `publicId()` UUID binding.
   - Responsive CSS layout in `clients.css` with clean grid/flexbox cards that gracefully stack vertically on viewport widths below 1024px, completely eliminating horizontal overflow.

4. **Lifecycle & Effective Status Presentation**:
   - Stored vs effective status disambiguation: active sites under inactive companies display unambiguous "Inactive (Company inactive)" status badge with appropriate ARIA label, while preserving underlying stored active status.
   - Inactive company rules: disables "New site" and site activation controls with explanatory hints; preserves site rename and site deactivation.
   - Company deactivation dialog includes explicit warning regarding effective site deactivation while preserving stored state.

5. **Validation, Safe Feedback & Anti-Double-Submit**:
   - Trimmed string validation (1-200 characters), control character detection, and duplicate submit button disablement during asynchronous RPCs.
   - Deterministic error feedback mapped from all `ClientManagementException.Reason` enum codes, completely eliminating stack traces, SQL, and internal infrastructure leakage.
   - Concurrent mutation (`STALE_VERSION`) handling: notifies administrator and refreshes state for re-evaluation.

6. **Load Failure Separation & Bounded Retry Elimination**:
   - Distinct failure handling paths for query loads (`handleCompanyLoadFailure`, `handleSiteLoadFailure`) versus mutation command results (`handleCompanyMutationException`, `handleSiteMutationException`).
   - `PERSISTENCE_FAILED` and unexpected query exceptions display safe generic feedback and stop cleanly with bounded invocation count.
   - `INVALID_PAGE` during loading performs a single bounded recovery to offset zero (`loadCompanies(false)` / `loadSites(false)`). If that recovery load fails, it halts safely without infinite recursion.
   - Mutation outcomes that trigger a refresh (`STALE_VERSION`, `CONFLICT`, `NOT_FOUND`, etc.) invoke bounded query loads. If the subsequent query encounters a failure, the load-error handler terminates safely without recursive retry loops.

7. **Selected-Company Site Ownership & Load Failure Invalidation**:
   - In `ClientAdministrationView`, when Company selection changes or when Site loading fails (`handleSiteLoadFailure`), obsolete Site state is invalidated via `invalidateSiteState()`: clearing the Site grid items, hiding the grid, empty label, and paging controls, resetting page tracking, and clearing `selectedSite`.
   - Fail-closed ownership guard: `isSiteOwnedByCurrentCompany(site)` verifies that `site.companyPublicId()` matches both `selectedCompanyId` and `selectedCompany.publicId()`. Mismatched or null references fail closed.
   - Site selection listener and action button enablement (`renameSiteBtn`, `toggleSiteLifecycleBtn`) strictly enforce `isSiteOwnedByCurrentCompany(selectedSite)`.
   - Mutation entrypoints (`openRenameSiteDialog`, `toggleSiteLifecycle`) and their inner execution callbacks guard against mismatched or stale Site references, failing closed before invoking any `ClientManagementService` mutation command.
