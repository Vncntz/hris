- a named scenario plus canonical options manifest;
- deterministic fictional public record identities;

- a lazy/streaming population path;

- documentation for future domain-specific extensions.

## Implementation direction

1. Refresh current `main` before implementation and verify the predecessor gate.

2. Keep implementation inside `tools/synthetic-data` except for documentation and predecessor/state reconciliation.

3. Add only dependencies justified by this task.

   Preferred production dependency:

   - repository `shared-kernel`, for neutral `PublicId` use where useful.

   Preferred test dependency:

   - `org.junit.jupiter:junit-jupiter`.

   Do not add a random-data/Faker library, database dependency, Spring Boot application dependency, or serialization framework merely for convenience.

4. Establish an explicit generator version.

   The initial version may be `1`.

   It must be part of dataset identity and must change when a future modification would make the same profile/seed/scenario/options produce materially incompatible logical output.

   Do not derive generator compatibility identity solely from `0.1.0-SNAPSHOT`.

5. Add named baseline profiles:

   - `S` — 2,000 active population identities;
   - `M` — 10,000;
   - `L` — 30,000;
   - `XL` — 100,000.

   These use the upper boundary of the frozen planning tiers so each baseline profile exercises its tier envelope.

   They remain workload-generation targets, not benchmark evidence.

   `TARGET — NOT YET BENCHMARKED`

6. Define a generator request with at least:

   - profile;
   - signed 64-bit deterministic seed;
   - named scenario;
   - scenario/options map.

   Provide a baseline scenario such as `baseline`.

   Validate scenario/option inputs rather than accepting null or ambiguous values.

7. Canonicalize scenario options.

   Equivalent option maps must produce the same dataset identity regardless of insertion order.

   Use explicit UTF-8 and a documented canonical ordering. Do not use platform-default encoding or line separators in deterministic identity calculation.

8. Define a dataset manifest containing at least:

   - generator version;
   - profile;
   - active population target;
   - seed;
   - scenario;
   - canonical options.

   Provide a deterministic canonical representation suitable for logs/artifacts and a deterministic SHA-256-style fingerprint/digest.

   A small dependency-free canonical text format is acceptable. Do not add JSON infrastructure solely because JSON might be convenient.

9. Implement deterministic fictional record identities.

   The core should be able to derive a stable sequence containing at least:

   - zero- or one-based ordinal;
   - deterministic `PublicId`;
   - visibly fictional stable label/code.

   These are generator/tool records, not Worker domain entities.

   Do not use `UUID.randomUUID()`, implicit random seeds, wall-clock time, default timezone, default locale, filesystem order, or process-specific data.

10. Keep the population API lazy or streaming.

    Requesting XL must not require constructing a 100,000-element business-object graph before iteration can begin.

    A stream/iterator/spliterator or equivalently bounded design is appropriate.

11. Synthetic labels must be visibly fictional.

    Use unmistakable forms such as `SYNTH-000001` rather than realistic names copied from external or customer sources.

12. Add golden deterministic tests.

    Tests must prove at least:

    - identical version/profile/seed/scenario/options produce identical canonical manifest and fingerprint;
    - different seeds produce a different dataset fingerprint/output;
    - equivalent option maps inserted in different orders remain equivalent;
    - known input produces a checked-in fixed expected fingerprint, so Linux and Windows CI independently exercise the same canonical result;
    - deterministic record IDs/labels are stable for known ordinals;
    - S/M/L/XL profile population values are exactly 2,000 / 10,000 / 30,000 / 100,000;
    - the XL path can iterate exactly 100,000 deterministic records without database access;
    - generated public identities are unique within that XL exercise;
    - production generator code contains no wall-clock/random UUID dependency;
    - no customer-derived fixture is required.

13. Do not turn the XL exercise into a performance assertion.

    Record no throughput, duration, memory ceiling, or product-capacity pass/fail claim from ordinary CI.

14. Document the generator in `docs/modules/synthetic-data.md`.

    Cover:

    - purpose and ownership;
    - generator-version rule;
    - dataset identity;
    - S/M/L/XL profile populations;
    - determinism rules;
    - fictional-data/privacy rule;
    - current baseline scenario;
    - current lack of business-domain persistence;
    - how later domain tasks should extend generation without making `shared-kernel` or the generator own business aggregates;
    - explicit statement that XL generation is not XL performance qualification.

15. Preserve the modular monolith.

    The synthetic-data tool may depend on neutral shared primitives. Business modules must not acquire a production dependency on this test/performance tool.
