## Goal

Implement the first focused Identity & Access foundation:

- database-backed local username/password authentication;
- adaptive Argon2id-targeted password hashing with an upgradeable encoded format;
- persistent failed-login and temporary-lock state;
- a bounded 30-minute default authenticated-session idle timeout;
- a stable authenticated user principal;
- a narrow authorization/current-actor API for later application-service boundaries;
- supported Vaadin/Spring Security login and navigation protection.

Do this without implementing IMP-013's user/role/permission administration or later MFA/SSO functionality.

## Implementation direction

1. Refresh current `main` before implementation and confirm V3 is still the next unused global migration version.

2. Verify the exact Spring Security and Vaadin security APIs against current official documentation compatible with the repository-managed Spring Boot 4.1.1 / Vaadin 25.3.0 baseline. Do not independently upgrade or pin framework versions.

3. Keep Identity & Access as the sole owner of authentication state and authenticated-principal semantics.

4. Add only required dependencies.

   Prefer:
   - Spring Security's supported servlet/security APIs;
   - JPA/Hibernate for normal Identity & Access persistence;
   - the selected Spring Security-compatible Argon2id implementation.

   If the selected Argon2 implementation needs an additional crypto library, verify the required dependency and repository dependency-management behavior before adding it. Do not guess a version.

5. Password storage must be one-way and upgradeable.

   - Never store plaintext or reversibly encrypted user passwords.
   - Encode new passwords using the verified Argon2id target.
   - Store an algorithm/version identifier with the encoded representation, for example through a correctly configured delegating encoder.
   - Do not use `NoOpPasswordEncoder`, `User.withDefaultPasswordEncoder()`, a hardcoded credential, or Spring Boot's generated default user as a production path.
   - Raw passwords must never be logged or audited.

6. Framework/default work-factor parameters may be used only as the initial engineering baseline if required to establish the implementation.

   They are not a production benchmark or security qualification.

   Record that password-hash work-factor calibration remains required on supported production hardware before production security qualification. Do not invent a measured result.

7. Implement only the minimum persistent account/security state required for authentication.

   The V3 account table should include deliberate representations for:
   - internal identity;
   - stable public UUID;
   - canonical login name;
   - encoded password hash;
   - enabled/disabled state;
   - failed authentication count/state;
   - bounded temporary lock-until UTC instant;
   - credential/security update metadata needed by this task;
   - concurrency/version field if required for correct updates.

   Do not add role, permission, role-assignment, MFA-secret, reset-token, or Worker-link tables in this task.

8. Canonicalize usernames deterministically without host-default locale dependence.

   Authentication of differently cased forms of the same supported login identifier must not create distinct accounts. Database uniqueness must enforce the canonical representation.

9. Failed authentication must not expose account existence.

   Unknown-user and wrong-password failures should expose the same ordinary external authentication failure semantics.

   If practical with the selected provider, perform appropriate dummy password verification for unknown users rather than creating an obvious timing shortcut.

10. Implement bounded repeated-failure protection.

   Initial configurable product defaults:
   - 5 consecutive failed password attempts before temporary lock;
   - 15-minute temporary lock duration.

   These are configurable product defaults, not statutory or external security requirements.

   Requirements:
   - successful authentication resets the consecutive-failure state;
   - a currently locked account cannot authenticate even with the correct password;
   - lock expiration uses an injected `Clock`;
   - lock state survives application restart;
   - disabled accounts cannot authenticate;
   - failure-state updates must not use an obviously lossy concurrent read/modify/write pattern.

11. Do not create a production bootstrap account.

   After V3 on a new database the user-account table may legitimately be empty. IMP-013 will own normal user/role/permission administration/provisioning.

12. Provide a stable authenticated principal carrying the user's public ID.

   Do not make Worker identity the authentication principal. User/account lifecycle remains independent from Worker lifecycle.

13. Expose a narrow application-facing authorization boundary from `identity-access`.

   It must allow later application services to:
   - obtain the current authenticated actor/public user ID;
   - test or require an authority/permission.

   Keep Spring Security implementation details behind this boundary where practical. Do not establish a business permission catalog or persistent role assignments in this task.

14. Prove authorization behavior with synthetic authorities.

   At minimum:
   - unauthenticated actor is rejected;
   - authenticated actor public ID is returned correctly;
   - a required synthetic authority succeeds when present;
   - the same check fails with normal access-denied behavior when absent.

15. Integrate `hris-app` with supported Vaadin/Spring Security configuration.

   Use `VaadinSecurityConfigurer` or the verified current equivalent rather than hand-rolling Vaadin internal-request exceptions.

   Add a minimal login view suitable only for establishing the authentication flow.

   Navigation baseline:
   - login view is anonymous;
   - normal application root requires authentication;
   - unannotated/new views must not accidentally become anonymous merely because a developer forgot authorization configuration.

16. Preserve framework protections.

   Do not globally disable CSRF, session-fixation protection, or Vaadin navigation access control merely to make tests pass.

17. Configure the D-151 default authenticated-session idle timeout as 30 minutes through the normal Spring Boot/servlet-session mechanism.

   Keep it externally configurable through the existing TASK-0010 convention.

   Do not add Redis, JDBC Spring Session, or another distributed session store.

18. Logout must invalidate/clear the authenticated session through standard Spring Security/Vaadin behavior.

19. Preserve the ordinary database-independent application smoke path.

   Update it to reflect the new security behavior, for example by proving the login bootstrap is served and the protected root redirects appropriately.

   Use test-only mocks/configuration where necessary. Do not weaken production security merely because the smoke test excludes the datasource.

20. Allocate:

   `V3__create_identity_access_authentication.sql`

   only after confirming V3 remains unused.

21. Update `MySqlDatasourceIT` for a three-migration history without weakening existing V1/V2 regression guarantees.

   Continue proving:
   - released V1 remains present and unchanged;
   - released V2 remains present and unchanged;
   - V3 applies successfully;
   - repeat `validate()` succeeds;
   - a second `migrate()` executes zero migrations;
   - the existing conflicting/duplicate V1 regression still fails as expected.

22. Add real-MySQL authentication verification using synthetic credentials.

   Prove at least:
   - clean migration through V3;
   - synthetic account row can be authenticated with the correct password;
   - stored credential is an encoded one-way value and is not equal to the supplied raw password;
   - wrong password fails;
   - repeated failure reaches temporary lock using task/test-controlled settings or the configured default;
   - correct password remains rejected while locked;
   - advancing an injected clock beyond lock expiry allows the correct password again;
   - successful authentication resets failure state;
   - disabled account remains rejected;
   - user public UUID and canonical login round-trip correctly.

## Security, privacy, audit, migration, and deployment

Authentication data is security-sensitive.

Never emit raw passwords, password hashes, entered credentials, future MFA secrets, reset/recovery material, or security answers into audit context, logs, diagnostics, exception messages, fixtures, or PR text.

Do not create authentication-event audit payloads containing raw login credentials. If a later task records security events through the existing `AuditRecorder`, it must use stable/minimized actor/target identifiers.

V3 is a forward-only migration creating Identity & Access authentication storage. No production-data transformation is authorized.

V1 and V2 remain immutable.

No installer, service, HTTPS, firewall, backup, or customer deployment change is authorized except documenting any new externally configurable security settings.

The existing V2 trigger-creation prerequisite on MySQL installations with binary logging remains unchanged.
