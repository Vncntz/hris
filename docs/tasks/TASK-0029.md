## Goal

Implement a reusable recent credential re-authentication boundary for sensitive Identity & Access administrative operations.

An authenticated administrator must prove the current credential in the current local HTTP session before existing `identity:admin` mutation services may execute. Successful proof creates only short-lived session-local non-secret freshness state.

The mechanism must be offline-capable, must not persist credential proof or session secrets, and must not weaken the existing authority, generation, session-revocation, transaction, or audit boundaries.

## Current implementation baseline

Identity & Access currently provides:

- adaptive Argon2id password verification and encoding;
- authenticated `CurrentActor` public UUID and authority checks;
- self-service password change with current-credential proof;
- administrative account creation;
- administrative account enable/disable;
- Account-to-Role administration;
- Role and Permission administration;
- Account and Role generation-based stale-authentication rejection;
- local `SessionRegistry` tracking and targeted expiry;
- 30-minute default authenticated-session idle timeout;
- append-only audit for administrative mutations.

`AccountPrincipal` retains only the Account public UUID and canonical login.

No successful-login or session state currently records recent privileged credential proof.

No existing administrative command requires a separate recent-credential proof after initial login.

No TOTP/MFA enrollment, challenge, recovery, administrator credential recovery/reset, or production password-cost qualification exists.

Current released migration history ends at V8.

No approved ADR changes this direction.

## Acceptance criteria

1. Introduce an Identity & Access application service that lets the currently authenticated user prove the Account's current password without accepting an Account UUID or login name from the caller.

2. `CurrentActor.requireUserId()` remains the sole source of the Account identity being re-authenticated.

3. Re-authentication accepts an owned mutable credential buffer and clears it on every success and failure path.

4. Password comparison must use the repository-managed adaptive `PasswordEncoder`; do not introduce plaintext comparison, alternate password storage, reversible encryption, or a second credential representation.

5. Refuse caller-held database transactions before performing adaptive password verification so expensive credential work does not occur while an unrelated caller transaction holds locks.

6. Verification must fail closed when the Account is missing, disabled, or otherwise unavailable.

7. A concurrent credential replacement must not allow stale credential proof to establish fresh privileged state.

8. After expensive password verification, use a short bounded `READ_COMMITTED` transaction and the existing Account locking/refresh conventions to recheck enabled state and the exact verified credential state before accepting proof.

9. A failed re-authentication attempt must not create or refresh recent-authentication state.

10. Beginning an explicit re-authentication attempt must invalidate any previous recent-authentication marker in that same session until the new proof succeeds.

11. Introduce a configurable privileged re-authentication freshness window through the existing security-policy configuration.

12. Use a baseline default of `PT5M`. Validate configuration fail-fast and reject non-positive values and values greater than `PT30M`.

13. The freshness decision must use the repository-injected `Clock`, not direct system-clock calls.

14. A clock rollback that places the stored proof time in the future must fail closed rather than extending freshness.

15. Recent-authentication state must be local to one authenticated HTTP session.

16. Re-authenticating one session must not authorize another concurrent session for the same Account.

17. Session-local state may contain only the authenticated Account public UUID and the proof timestamp required for freshness evaluation.

18. Do not retain the raw password, password hash, canonical login, authorities, database IDs, HTTP session identifier, CSRF token, MFA material, or arbitrary request data in the recent-authentication marker.

19. Do not persist recent-authentication state to MySQL, audit tables, files, caches, cookies, or another infrastructure service.

20. New authentication must begin without privileged recent-authentication state.

21. Logout, session invalidation, normal session expiry, application restart, and existing targeted security-session revocation must naturally discard the state with the local servlet session.

22. Provide an Identity-owned guard that first derives the authenticated actor and then rejects a missing, mismatched, expired, or future-dated recent-authentication marker with a bounded non-secret application failure.

23. Existing authorization remains independent: recent credential proof alone never grants `identity:admin` or any other authority.

24. Existing administrative services must continue to require `identity:admin` and must additionally require recent re-authentication before mutation for:
    - ordinary Account creation;
    - Account enable/disable;
    - Account-to-Role assignment/removal;
    - Role creation and enable/disable;
    - Permission creation;
    - Role-to-Permission assignment/removal.

25. Authorization must be checked before the recent-authentication guard so an unauthorized caller is not converted into an authenticated-but-needing-proof administrative caller.

26. First-administrator provisioning remains outside this guard because it executes before an authenticated administrator exists.

27. Self-service password change remains outside this guard because it already requires proof of the current credential in the same command.

28. Recent re-authentication itself is credential verification, not an administrative data mutation. Do not add an append-only business audit event solely for successful or failed proof in this task.

29. Existing administrative mutation audit events remain unchanged and continue to identify the authenticated administrator rather than the credential-proof mechanism.

30. Do not mutate Account credential, canonical login, enabled state, role membership, failure/lock state, Account authentication generation, Role authorization generation, or audit history merely because re-authentication succeeds.

31. Credential-proof failure reasons must be bounded and must not expose whether a supplied password differed from the stored hash through infrastructure exception text.

32. Do not log or place credential values/hashes, session identifiers, authentication tokens, or private security state in exceptions, audit context, test names containing runtime values, Maven output, or committed fixtures.

33. Existing account-disable, password-change, Account-role, and Role-authority session invalidation behavior must continue to make an expired session unusable regardless of any earlier recent-authentication marker.

34. Do not add a distributed session store, Redis, database-backed session state, messaging system, queue, microservice, or other infrastructure dependency.

35. No Flyway migration is expected. Released V1–V8 must remain byte-for-byte unchanged.

36. No new cryptography/MFA dependency is expected for this task.

37. Focused unit tests must cover successful proof, wrong credential, disabled/missing Account, stale concurrent credential state, buffer clearing, persistence failure, configuration bounds, exact expiry boundary, clock rollback, actor mismatch, missing session state, session independence, marker replacement, and bounded failures.

38. Existing administrative-service unit tests must prove the additional recent-authentication requirement without weakening their existing authorization, audit, rollback, generation, or concurrency assertions.

39. Real-MySQL/HTTP verification must prove at least:
    - authenticated administrator denied a protected administrative mutation before re-authentication;
    - wrong credential does not establish freshness;
    - successful current-credential proof permits the mutation;
    - a second concurrent session for the same Account remains unproven;
    - expiry of the configured freshness window denies a later administrative mutation;
    - logout/new authentication begins unproven;
    - concurrent password replacement cannot leave a usable stale recent-authentication proof;
    - existing session revocation makes an earlier proof unusable.

40. Existing AccountAuthenticationIT, PasswordChangeIT, AccountLifecycleIT, AccountRoleAssignmentIT, RoleAdministrationIT, first-administrator, authorization, migration, audit, architecture, session-fixation, CSRF, logout, and MySQL regressions must remain green.

41. Keep production transport out of scope. A test-only HTTP adapter may be used to prove real session behavior, but do not add a Vaadin administration view or REST endpoint in this TASK.

42. Update applicable mutable Identity module documentation, TASK/IMP/state/routing records, tests, and configuration documentation with verified facts.

## Security, privacy, and audit implications

This TASK reduces the impact of a stolen but still-valid privileged session by requiring proof of the current Account credential close to sensitive Identity administration.

Recent proof does not replace authorization and does not create authority.

Credential material remains ephemeral. Only Account public UUID plus proof timestamp may be stored as session-local freshness state.

The underlying administrative action remains the auditable mutation; the proof itself does not create a new append-only business event.
