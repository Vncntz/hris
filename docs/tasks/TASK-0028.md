## Goal

Provide authenticated Identity & Access application-service boundaries for the remaining core RBAC administration required to create Roles and Permission definitions, enable/disable Roles, and add/remove Role-to-Permission membership.

Every Role mutation that can change effective authorities must invalidate stale authenticated authority snapshots for Accounts assigned to that Role without requiring an O(number-of-accounts) authentication-generation write fan-out.

This task introduces a dedicated Role authority generation and integrates it with authentication, final servlet-session registration, affected-session expiry, and deterministic concurrency handling.

## Current implementation baseline

V5 owns:

- `identity_role`;
- `identity_permission`;
- `identity_account_role`;
- `identity_role_permission`.

Role has a stable public UUID, canonical unique name, enabled state, optimistic row version, and Permission membership.

Permission has a unique canonical authority key. The authority key is its stable authorization identifier; Permission currently has no public UUID.

TASK-0022 loads all assigned Roles and derives effective authorities only from enabled Roles.

V7 supplies `identity_account.authentication_generation`. TASK-0025/TASK-0026/TASK-0027 use it to reject stale final registration for Account-specific security changes.

TASK-0027 uses `AuthenticatedSessionRevoker` to expire every locally tracked session for one affected Account.

No authenticated Role-management, Permission-definition, or Role-to-Permission administrative service currently exists.

Final servlet registration currently validates only the Account authentication generation. A Role enable/disable or Role-to-Permission mutation can therefore change the meaning of an already-created authority snapshot without changing the Account generation.

No approved ADR changes this direction.

## Acceptance criteria

1. Add authenticated Identity & Access application-service boundaries for:
   - creating a Role;
   - enabling an existing Role;
   - disabling an existing Role;
   - creating a Permission definition by canonical authority key;
   - assigning an existing Permission to an existing Role;
   - removing an existing Permission from an existing Role.

2. Every administrative command must first require `CurrentActor.requireAuthority("identity:admin")` and derive its audit actor only from `CurrentActor.requireUserId()`. Caller-supplied actor identifiers must never affect authorization or audit attribution.

3. Cross-boundary targeting must use only:
   - Role stable public UUID;
   - Role name when creating a new Role;
   - Permission canonical authority key.
   Do not expose or accept internal relational IDs.

4. Ordinary administrative Role creation must produce:
   - a new stable public UUID;
   - a canonical unique Role name;
   - a disabled Role by default;
   - zero Permission assignments;
   - authentication/authority generation zero.
   Starting disabled is the least-privilege default and permits configuration before activation.

5. Permission creation must create only a canonical unique authority key. Do not create a complete future-module Permission catalog, seed business Permissions, or introduce customer-specific authorization definitions through migration.

6. Duplicate Role names, duplicate Permission keys, missing Role/Permission targets, enable/disable no-ops, duplicate Role-Permission assignment, missing Role-Permission membership, invalid canonical inputs, authorization failure, persistence failure, audit failure, and session-revocation failure must expose bounded non-secret outcomes without SQL, internal IDs, stack causes, credentials, hashes, login names, or session IDs.

7. Role rename and Role/Permission deletion are not part of this task. Permission authority keys created here are immutable through this administrative boundary.

8. Allocate the next available global migration version for a dedicated Role authority generation. On current `main`, the expected migration is:
   `V8__add_identity_role_authorization_generation.sql`.

9. V8 must add only a non-secret nonnegative `BIGINT NOT NULL DEFAULT 0` authority-generation scalar to `identity_role`, with an appropriate database constraint. Existing Roles receive generation zero. V8 must not seed or modify Accounts, Roles, Permissions, memberships, credentials, customer data, or other production authorization state.

10. Released V1–V7 are immutable. If another migration reaches `main` before implementation starts, refresh `main`, allocate the next unused forward version, and rerun the complete migration verification rather than rewriting released history.

11. Role enable/disable and every Role-to-Permission assignment/removal must advance the affected Role authority generation exactly once in the same transaction as that Role authority mutation. Rejected/no-op operations must not advance it.

12. Role creation and standalone Permission creation do not change any existing Account's effective authorities and therefore must not revoke sessions or advance another security generation.

13. Authentication must capture a transient Role authority-generation snapshot for every Role currently assigned to the Account, including disabled assigned Roles. Effective authorities remain derived only from enabled Roles.

14. The transient registration snapshot must contain only non-secret Role public UUID/generation data required to prove freshness. It must not add credentials, password hashes, session IDs, internal database IDs, or arbitrary Role/Permission dumps to persistent session state.

15. Final servlet-session registration must validate:
   - the existing Account authentication generation; and
   - the exact authority-generation snapshot for all Roles assigned at authentication.
   Account membership changes remain protected by the Account generation established by TASK-0027.

16. Final registration and Role authority mutation must use deterministic database locking or an equivalently strong serialization mechanism so that a pre-mutation authentication cannot become a usable post-mutation session.

17. Lock Roles in deterministic order when a registration must validate multiple assigned Roles. Do not introduce order-dependent deadlocks between concurrent registrations.

18. Coordinate Account-to-Role assignment with Role mutation so the membership cannot race a Role authority change into a stale state. Reuse the existing Role repository/locking boundary or an equivalently narrow Identity-owned mechanism; do not add a distributed lock or external cache.

19. Role-wide authority mutation must identify Accounts currently assigned to the changed Role and expire all locally tracked sessions for those affected Accounts before transaction completion.

20. Extend the existing local session-revocation abstraction so a Role-wide mutation can revoke an affected UUID set with a single bounded scan of the local `SessionRegistry`, rather than scanning the registry independently once per Account.

21. Role-wide authority mutation must not update every affected Account's `authentication_generation`. The Role authority generation is the security version for Role-wide changes; Account generation remains the security version for Account-specific credential/lifecycle/membership changes.

22. Unrelated Account sessions must remain unexpired. There is no broad “logout everyone” fallback for an ordinary successful Role mutation.

23. A Role disable or removal of `identity:admin` from a Role must reject before mutation when the authenticated administrator is assigned to that Role and the resulting persisted enabled Role/Permission set would leave that administrator without effective `identity:admin`.

24. Self-admin protection must evaluate persisted enabled Role/Permission state, not Role names, the current token's possibly stale authority snapshot, or special treatment of the bootstrap Role name.

25. Enabling a Role and adding a Permission may grant new authority. Disabling a Role and removing a Permission may revoke authority. In every case, affected Accounts obtain the new effective authority set only after fresh authentication.

26. Each successful administrative mutation records exactly one privacy-minimized audit event:
   - Role creation: `IDENTITY_ROLE_CREATED`;
   - Role enable: `IDENTITY_ROLE_ENABLED`;
   - Role disable: `IDENTITY_ROLE_DISABLED`;
   - Permission creation: `IDENTITY_PERMISSION_CREATED`;
   - Role-Permission assignment: `IDENTITY_ROLE_PERMISSION_ASSIGNED`;
   - Role-Permission removal: `IDENTITY_ROLE_PERMISSION_REMOVED`.

27. Audit targets must use stable non-secret identifiers:
   - Role events: target type `IDENTITY_ROLE`, target reference Role public UUID;
   - Permission creation: target type `IDENTITY_PERMISSION`, target reference canonical authority key;
   - Role-Permission membership: target type `IDENTITY_ROLE_PERMISSION`, target reference Role public UUID; include the canonical authority key only in the bounded context described below. A UUID/key concatenation can exceed the existing 128-character target-reference limit and must not be used or truncated.
   Actor is the authenticated administrator public UUID and reason is `null`.

28. Use these exact contexts:
   - `administrative-role-management`;
   - `administrative-permission-management`;
   - `administrative-role-permission-assignment/<canonical-authority-key>` for assignment/removal.
   The fixed prefix plus one canonical non-secret key remains within the existing 1024-character context limit; maximum-length 128-character keys must be accepted and audited intact without changing the audit schema.
   Do not record account login names, credentials/hashes, session identifiers, internal database IDs, arbitrary request serialization, or authority snapshots.

29. Role authority mutation, generation advancement, and its audit event must flush successfully before affected sessions are expired.

30. Session-revocation failure must fail closed and roll back the Role/Permission membership mutation, Role authority-generation change, and audit event. Sessions already expired before a failure may remain expired.

31. If a database commit fails after sessions have been successfully expired, the database may retain its preceding Role/Permission state while those sessions remain expired. Document and test this safe non-atomic asymmetry; fresh authentication then uses the retained database state.

32. Deterministically prove both final-registration ordering classes:
   - registration completes first, then the Role mutation observes and expires the registered affected session;
   - Role mutation owns the serialization lock first, then old authentication fails final registration because its Role generation is stale.
   Do not use sleep-based race assertions.

33. Deterministically cover concurrency between TASK-0027 Account-to-Role membership changes and TASK-0028 Role authority mutations so neither ordering can create a usable stale authority snapshot.

34. Preserve Account public UUID, canonical login, credential/hash, enabled state, security timestamps, failure/lock state, Account authentication generation, and unrelated Account memberships during Role-wide authority changes.

35. Preserve Role public UUID and canonical name during enable/disable and Permission-membership commands. Permission assignment must not implicitly enable a Role.

## Security, privacy, and audit implications

Role/Permission administration is a security-boundary mutation and remains protected by `identity:admin`.

Existing authenticated authorities are session snapshots. The Role authority generation protects in-flight authentication from Role-wide semantic changes while targeted local expiry removes already-established affected sessions.

The design deliberately avoids rewriting every Account row for a Role-wide change.

Only stable non-secret identifiers required for freshness or audit may cross application boundaries.

No real customer data, reusable production credential, secret, MFA material, password hash, or session identifier may appear in source, fixtures, logs, documentation, CI artifacts, or AI context.
