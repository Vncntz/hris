## Goal

Align server-side Vaadin route authorization with the persisted permission authorities already supplied by Identity & Access so protected Vaadin routes can use exact permission names such as `client:admin`.

The integration must use the existing authority namespace directly. It must not rename persisted permissions, generate duplicate authorities, translate them into a parallel `ROLE_*` model, seed new permission assignments, or weaken route authorization.

## Relevant baseline and contracts

Identity & Access exclusively owns security principals and authorization under D-089. The technology baseline remains Java 25, Spring Boot 4.1, Vaadin 25.3, MySQL 8.4 and Maven under D-108.

Current-main contracts:

- `SecurityCurrentActor.hasAuthority(String)` compares the requested string exactly with `GrantedAuthority#getAuthority()`.
- `SecurityCurrentActor.requireAuthority(String)` remains the backend/application authorization boundary.
- `SecurityConfiguration` owns the Vaadin/Spring Security integration and existing `/login` flow.
- `/login` is `@AnonymousAllowed`.
- `MainLayout` and `DashboardView` are currently authenticated through `@PermitAll`.
- `MainLayout` renders Vaadin's access-filtered menu configuration.
- Menu visibility is supplementary; direct route authorization must remain server-side enforced.
- TASK-0041 independently owns login-view presentation changes.

Route authorization must complement, not replace, backend service-level authorization. Business operations requiring an authority must continue enforcing it through the existing application/backend boundary even when the invoking Vaadin route is also protected.

## Acceptance criteria

1. A focused protected Vaadin test route using the exact permission name `client:admin` through the repository-supported Vaadin route authorization annotation/access mechanism is authorized for an authenticated synthetic principal carrying `GrantedAuthority("client:admin")`.

2. Authorization succeeds without requiring or synthesizing `ROLE_client:admin`, without renaming `client:admin`, and without introducing another role/permission mapping layer.

3. An authenticated synthetic principal lacking `client:admin` cannot directly navigate to the protected route. Denial is enforced server-side using normal Vaadin/Spring Security failure behavior and does not expose protected route content or security internals.

4. An anonymous principal cannot directly access the protected route and receives the existing login/denial behavior appropriate to the Vaadin request flow.

5. Existing behavior remains intact: `/login` stays anonymously accessible; authenticated access to the existing `@PermitAll` shell/dashboard continues to work; no TASK-0041 login behavior or browser-DOM factor contract changes.

6. Vaadin menu/access filtering and actual direct-route authorization agree for the focused protected route: an authorized principal may see/use the entry when applicable, while an unauthorized principal is not presented an entry that it cannot open. Menu hiding never substitutes for the server-side route check.

7. Existing `CurrentActor` exact-authority behavior remains unchanged. Existing Identity & Access security tests continue to pass, including exact synthetic authority checks.

8. Focused tests are deterministic and use only synthetic principals and authorities. They cover authorized, authenticated-but-unauthorized, and anonymous cases without production users, persisted production assignments, credentials, or real customer information.

9. No frontend implementation, product CRUD, RBAC redesign, new permission seeding, persistence/schema change, or unrelated module behavior is introduced.

## Security, privacy and audit

Authorization must fail closed for missing or insufficient authority.

Direct route authorization remains server-side. Access-filtered navigation is not an authorization boundary by itself.

Do not leak required permissions, internal identifiers, credentials, authentication factors, stack traces, infrastructure details, or production assignment information through denial behavior.

Do not weaken existing backend `requireAuthority(...)` checks merely because a route is protected.

No new business audit event is required solely for framework-level route allow/deny decisions unless an existing repository security contract already requires it. Do not add sensitive authorization/session data to logs or audit payloads.

Use synthetic identities and authority strings in all tests.
