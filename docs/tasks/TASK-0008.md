# TASK-0008 — Flyway foundation and global migration ordering

Status: PLANNED — implementation blocked until this planning PR merges and passes required post-merge CI

Parent implementation item: [IMP-005](../implementation/tasks/IMP-005.md)

## Goal

Add the smallest Flyway foundation to the existing one-application, real-MySQL/Testcontainers baseline. Establish a single globally ordered migration stream and prove its history and validation behavior on disposable MySQL without introducing business schema.

## Non-goals

- No business/domain tables, entities, repositories, seed data, or module behavior merely to exercise Flyway.
- No production upgrade orchestration, maintenance mode, recovery-set creation, backup/restore implementation, or in-place downgrade.
- No application installer, customer deployment, persistent development database, or environment/secrets framework.
- No later IMP work, including shared primitives, audit, identity, or domain implementation.

## Affected modules and files

Expected implementation is limited to `hris-app` Maven dependencies/configuration, its migration resources and focused integration tests, a root POM change only if shared management is necessary, and narrow migration/developer documentation. Reuse the existing `mysql-it` Testcontainers activation and CI topology. Do not add Flyway to every business module or create competing module-local histories. Exact Flyway artifacts, versions, and resource paths must be verified against the then-current Spring Boot/Flyway/MySQL compatibility and repository layout before implementation.

## Relevant decisions and documents

Frozen Master Plan §35 and §65.1, D-143, D-144, and D-157; [IMP-005](../implementation/tasks/IMP-005.md), [IMP-004](../implementation/tasks/IMP-004.md), [execution rules](../implementation/EXECUTION_RULES.md), and [migration documentation index](../migrations/README.md). No approved ADR applies. Use the generated planning index and targeted retrieval for any additional frozen decision.

## Implementation direction

1. Define one authoritative location and allocation rule for monotonically ordered, versioned Flyway migrations across modules. Specify filename/version conventions, ownership, collision resolution, and the rule that released migrations are immutable; corrections use later forward migrations.
2. Wire Flyway only where the deployable application needs it. Preserve database-independent ordinary smoke verification and existing Windows/Linux CI behavior while the dedicated MySQL activation proves actual migration behavior.
3. If an executable migration is needed to prove ordering/history, use one minimal technical, non-business migration. Document its purpose and avoid artificial domain schema.
4. Use a disposable MySQL 8.4 LTS-line database to prove initial application, resulting Flyway history, repeat validation without reapplication, and visible failure on conflicting or modified history. Test the convention at the smallest meaningful layer; do not simulate MySQL with H2.

## Acceptance criteria

1. Compatible Flyway/MySQL dependencies and startup behavior are verified from current authoritative upstream documentation before pinning or wiring; dependency scope remains in `hris-app`.
2. One global migration stream is documented and enforced by the implementation/test design. Version collisions and edits to applied migrations fail rather than silently proceeding.
3. A clean disposable real-MySQL instance applies the technical baseline deterministically, records expected Flyway history, and validates it on a second run without changing it.
4. The test proves an actual MySQL connection and does not create business schema or require manual database setup.
5. Existing ordinary smoke/reactor verification remains valid; the MySQL migration test runs through the checked-in Maven Wrapper under `mysql-it` and in Ubuntu PR CI. Windows runs its ordinary reactor path.
6. Test credentials and data are disposable and synthetic. No secrets or production customer data enter source, logs, or CI artifacts.
7. Migration conventions, local commands, and the boundary with later upgrade/recovery work are documented. Frozen planning sources and existing released migrations are unchanged.

Verify exact-head `ci / policy`, `ci / build-linux`, and `ci / build-windows`, including the Linux MySQL migration test and Windows smoke test. ## Security, privacy, audit, migration, and deployment

No authentication, authorization, audit feature, customer deployment, or production data operation is introduced. The first technical migration, if used, enters the versioned migration history and must be treated as immutable once released. Production upgrade sequencing, maintenance mode, backup and restore qualification, and deployment remain separately scoped work. Record actual migration evidence and limitations after implementation; do not claim them from this planning document.
