## Goal

Ensure one failed ordinary HTTP username/password login attempt contributes exactly one eligible failed-attempt increment to the existing Account lockout policy.

The configured failed-attempt threshold must correspond one-for-one with actual failed login submissions. Ordinary form login must not reach temporary lockout early because the same authentication request is processed more than once.

## Current implementation baseline

Current `main` is `e65edb1da76844e38891845ba147c4b9c0cb7b1b`.

`AccountAuthenticationService.authenticate(...)` records one failure when one invocation receives a wrong credential for an enabled, unlocked Account.

`AccountAuthenticationProvider` delegates one provider invocation to that service.

The web `SecurityConfiguration` explicitly registers that provider with `HttpSecurity`; the provider is also a Spring-managed component. Treat duplicate effective provider registration as an investigation hypothesis, not an assumed root cause.

Existing `AccountAuthenticationIT` exercises successful HTTP form login, while most failure/lockout assertions invoke the production provider directly. The real HTTP failed-login path therefore lacks a regression proving one request equals one failed attempt.

D-151 governs bounded failed authentication and temporary locking. D-143 requires real MySQL coverage where framework/database behavior matters. D-148 requires tests, documentation and operational consequences before completion.

## Scope

Reproduce the failed-login overcount through the application's actual `/login` form-processing path against real MySQL.

Inspect the effective Spring Security authentication-provider composition and determine why one HTTP request can perform more than one eligible Account authentication attempt.

Apply the smallest repository-consistent correction so one ordinary failed form submission results in one authentication-service attempt and one eligible persisted failure.

Preserve the existing Account authentication service, lockout model, authority propagation, session registration, authentication-generation checks and TASK-0032 recent-re-authentication behavior.

## Acceptance criteria

1. Before changing production behavior, add or establish a deterministic real-HTTP/MySQL reproduction on current `main` showing the reported overcount. If clean current `main` cannot reproduce it, stop and report the finding rather than making a speculative provider-wiring change.

2. For a known enabled and initially unlocked Account, one wrong HTTP form-login POST changes `failed_attempts` by exactly one.

3. With a configured threshold of N, N-1 distinct failed form-login requests leave the Account unlocked and the Nth request establishes the configured temporary lock. No earlier request may lock the Account.

4. The correction must remove the duplicate processing cause rather than masking it through request IDs, credential deduplication, sleeps, in-memory counters, or changes that could discard legitimate concurrent attempts.

5. Direct `AccountAuthenticationProvider` / `AccountAuthenticationService` behavior remains one invocation equals one eligible failure.

6. Unknown, malformed, disabled, locked and wrong-password logins continue to expose the same bounded external authentication failure. Unknown/malformed identities retain dummy-hash behavior and cannot mutate Account state.

7. An already active temporary lock remains authoritative and is not extended or incremented merely by another rejected ordinary login.

8. Successful authentication after normal lock expiry retains existing recovery semantics: failed-attempt/expired-lock state is cleared and normal authorities, authentication generation, role generations, session fixation protection and session registration continue to work.

9. TASK-0032 cross-path behavior remains intact: ordinary-login locks block recent re-authentication, and locks created through recent re-authentication remain honored by ordinary login.

10. Do not change the configured failed-attempt threshold, lock duration, password policy, Argon2 representation or operational defaults.

11. No new business audit event is introduced for ordinary authentication success or failure. Existing security bookkeeping remains security state rather than an administrative business mutation.

12. No credential, password hash, authentication token, session identifier or other private security value may enter logs, audit context, exception details, committed fixtures or documentation.

13. No schema change or Flyway migration is expected. Released V1-V8 must remain unchanged.

14. No new authentication, cryptography, cache, queue, distributed-session or infrastructure dependency is expected.

15. Focused tests must cover the actual form-login failure path, exact persisted increment, exact threshold boundary, active-lock behavior and post-expiry recovery. Existing authentication and recent-re-authentication unit/integration regressions must remain green.

16. Run the required ordinary Windows reactor, Linux `mysql-it` verification, repository tooling/planning checks and relevant focused tests. Inspect actual Surefire/Failsafe results rather than relying only on Maven exit status.

17. Review the full diff for provider composition, authentication ordering, lockout correctness, session behavior, credentials/privacy exposure and scope.

18. Completion requires exact-final-head policy/Linux/Windows CI, every trusted-main integration gate, protected PR integration, and successful policy/Linux/Windows `push` CI on the exact merge SHA.
