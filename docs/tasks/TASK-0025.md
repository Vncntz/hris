# TASK-0025 - Authenticated password change and session revocation foundation

Status: Complete / POST_MERGE_VERIFIED - corrective PR #45 and exact-head/exact-merge CI independently verified.

Parent implementation item: [IMP-013](../implementation/tasks/IMP-013.md)

## Goal and scope

Add an authenticated Identity & Access application-service boundary for a signed-in account to change only its own password after proving knowledge of its current credential. Establish reusable local authenticated-session revocation so a successful credential change expires every tracked session for that account, including the caller, and requires fresh authentication with the new credential.

Identity & Access owns credential validation, credential mutation, session/security behavior and the application-service contract. Continue using the existing adaptive PasswordEncoder, `CurrentActor`, `AccountPrincipal`, account persistence and shared-kernel `AuditRecorder`.

The operation is self-service only. It accepts no target account identifier, login, actor override, role, permission, enabled-state or administrative privilege parameter.

Preserve the existing single-node servlet-session architecture. Use supported Spring Security session tracking in memory and retain unlimited concurrent-session semantics; do not introduce Redis, Spring Session, a distributed session service or another deployable component.

## Acceptance criteria

1. The password-change application-service boundary requires an authenticated supported `AccountPrincipal` and obtains the target/actor exclusively through `CurrentActor.requireUserId()`. The authenticated account may change only its own credential. Accept no login, target UUID, actor override or authority shortcut. Anonymous or unsupported authentication is rejected before credential verification, encoding or persistent mutation.

2. Accept the current password, new password and confirmation as owned mutable character buffers. Reuse the Identity-owned new-credential validation established by TASK-0023/TASK-0024: default minimum 12 and maximum 128 Unicode code points, exact confirmation, malformed-surrogate rejection and no trimming, case folding or truncation. Clear all three owned buffers on every exit path, including authorization, validation, current-credential, encoding, concurrency, audit, persistence and session-revocation failures. Secret-bearing request/result/exception types must not expose plaintext, hashes or printable credential serialization.

3. Verify the supplied current credential against the authenticated account's stored encoding using the existing adaptive PasswordEncoder without holding a write lock. Encode the validated new credential outside the mutation transaction. Do not expose the stored encoding outside Identity & Access.

4. Prevent lost credential updates. Capture the credential state used for current-password verification, then execute a short `REQUIRES_NEW`, READ COMMITTED mutation transaction that locks the authenticated account by stable public UUID. Before mutation, confirm the persisted credential still matches the verified snapshot and that the account remains enabled. A concurrent credential change must fail closed rather than overwrite the newer credential. No bounded retry may blindly repeat credential verification.

5. On successful mutation, replace only the authenticated account's password encoding, update credential/security timestamps using the injected Clock, and clear failed-attempt/temporary-lock state so the newly established credential can immediately authenticate. Preserve the account public UUID, canonical login, role assignments and all unrelated identity state.

6. Commit the credential mutation and exactly one privacy-minimized `IDENTITY_PASSWORD_CHANGED` audit event together. Actor and target are the authenticated account public UUID; target type is `IDENTITY_ACCOUNT`; context is fixed self-service password change. Never record current/new passwords, hashes, login text, request serialization or arbitrary user-supplied audit context. Audit failure rolls back the credential mutation.

7. Establish standard Spring Security servlet-session tracking using the repository-managed framework APIs. Use an in-memory session registry and normal servlet session lifecycle events. Configure tracking without imposing a new concurrent-session limit; preserve the existing effective unlimited-session behavior, 30-minute default idle timeout, session-fixation protection, CSRF and normal logout behavior.

8. After credential update and audit persistence have flushed successfully, expire every tracked authenticated session whose `AccountPrincipal` public UUID matches the changed account, including the calling session, before allowing the database mutation to complete successfully. If session-expiry marking fails, fail closed and roll back the database mutation. If a later database commit failure occurs after sessions have already been marked expired, the credential remains unchanged and the affected user may need to authenticate again with the old credential; document and test this safe fail-closed asymmetry. Do not revoke unrelated accounts' sessions.

9. A successful operation does not preserve an authenticated session. Subsequent use of every previously authenticated browser session for that account must require authentication again. The old password must no longer authenticate and the new password must authenticate after the commit. Session revocation is local to the single application process; application restart already destroys local servlet sessions and no distributed-session behavior is required.

10. Return only bounded non-secret outcomes. Wrong current credential, stale concurrent credential state, encoding failure, persistence/audit failure and session-revocation failure must not expose internal exception causes, password material, hashes, SQL details or session identifiers to an application caller.

11. Focused tests must prove authentication/actor enforcement, self-only targeting, new-credential validation, current-password rejection, encoder/transaction ordering, concurrent-change protection, timestamp/lock-state behavior, buffer clearing on every success/failure category, non-secret result/error behavior and unchanged role/authority state.

12. Real-MySQL verification must prove successful credential replacement, old/new authentication behavior, atomic audit rollback, concurrent stale-change rejection, preservation of unrelated identity/bootstrap/audit state and no schema drift. Application-security integration must create multiple real authenticated HTTP sessions for one account, prove they are tracked, perform a successful password change, and prove every prior session is expired while an unrelated account's session remains usable.

13. Existing account creation, first-administrator provisioning, authentication/lockout, persisted authority derivation, zero-authority accounts, CSRF, session timeout, audit, Flyway and architecture regressions remain green. Tests use only generated ephemeral synthetic credentials; no reusable production-like credential, hash or session identifier may enter source, logs, reports, documentation or CI artifacts.

14. Update applicable mutable module, TASK, IMP, implementation-state and routing records with actual verified behavior only. Completion requires required local verification, exact-final-head policy/Linux/Windows CI, clean trusted-main gates, protected PR integration and successful push CI on the actual merge SHA.
