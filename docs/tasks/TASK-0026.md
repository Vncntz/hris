# TASK-0026 — Administrative account enable/disable lifecycle and stale-authentication invalidation

Status: POST_MERGE_VERIFIED / complete.

Parent implementation item: [IMP-013](../implementation/tasks/IMP-013.md)

## Goal and scope

Add the authenticated Identity & Access application-service boundary for an administrator to enable or disable an existing account by stable public UUID.

Use the existing `identity:admin` authority, `CurrentActor`, `AccountEntity`, account persistence, append-only `AuditRecorder`, local `AuthenticatedSessionRevoker`, and standard servlet-session architecture.

A lifecycle transition must invalidate every authentication and session established from security state that predates that transition. This includes an authentication that has already verified a credential but has not yet completed servlet-session registration.

Introduce a dedicated persisted authentication generation for this purpose. Password replacement and account enable/disable transitions advance it. Ordinary successful or failed authentication attempts do not advance it.

Keep User/account identity separate from Worker identity. This task does not implement Worker linkage or employment-driven account lifecycle.

## Acceptance criteria

1. Provide an authenticated Identity & Access command boundary for administrative account lifecycle changes. Require `CurrentActor.requireAuthority("identity:admin")` and derive the audit actor exclusively from `CurrentActor.requireUserId()`. Accept only the target account's stable public UUID plus the explicit lifecycle operation. Accept no login text, actor override, authority shortcut, password, role, permission, Worker identifier, or arbitrary audit context.

2. Support explicit enable and disable operations. Missing targets, unauthorized callers, unsupported authentication, already-enabled/already-disabled state, self-disable attempts, persistence failures, audit failures, and session-revocation failures must produce bounded non-secret outcomes without exposing SQL, credentials, session identifiers, internal exception causes, or account login text.

3. An authenticated administrator must not be able to disable its own currently authenticated account. Reject self-disable before persistent mutation or session revocation. This prevents the only authenticated administrator from accidentally invalidating its own access before later assignment-administration safeguards exist.

4. Add a forward Flyway migration, expected as V7, adding a dedicated non-secret authentication generation to `identity_account`. Use a normal relational scalar such as `BIGINT NOT NULL DEFAULT 0`. Existing accounts must receive a valid initial value without introducing accounts, credentials, assignments, or customer data. Released V1 through V6 remain byte-for-byte unchanged.

5. Model the authentication generation inside Identity & Access and keep it out of durable authenticated session state. Authentication captures the current generation as transient request-only metadata. Final servlet-session registration revalidates it under the existing account row lock and removes the transient metadata before security-context persistence.

6. Password replacement must advance the authentication generation in the same transaction that changes the credential. Preserve `credential_updated_at_utc` as the actual credential-update timestamp; do not falsify it merely to invalidate authentication. Routine successful/failed login bookkeeping and temporary-lock updates must not advance authentication generation, so valid concurrent ordinary logins remain possible.

7. Every committed account enable or disable transition must advance the authentication generation. This invalidates authentication work begun against the immediately preceding lifecycle state, including a login that verified while enabled and attempts to register after a disable→enable sequence.

8. Execute lifecycle mutation in a short standalone `REQUIRES_NEW`, READ COMMITTED transaction using the repository's existing transaction conventions. Lock the target account by stable public UUID and explicitly refresh the managed entity under that lock before state checks, preserving the servlet-bound persistence-context protection established by TASK-0025. Do not blindly retry business validation.

9. Disabling changes only the account's enabled/security state and authentication generation. Preserve public UUID, canonical login, password encoding, credential-update timestamp, role assignments, permissions, and unrelated identity state.

10. Enabling changes only the enabled/security state and authentication generation and clears failed-attempt/temporary-lock state so the restored account can authenticate immediately with its unchanged current credential. Preserve public UUID, canonical login, credential, role assignments, and permissions.

11. Record exactly one privacy-minimized audit event for each successful transition: `IDENTITY_ACCOUNT_DISABLED` or `IDENTITY_ACCOUNT_ENABLED`. Actor is the authenticated administrator public UUID; target type is `IDENTITY_ACCOUNT`; target reference is the affected account public UUID; context is fixed administrative lifecycle context. Never audit login text, credentials/hashes, session identifiers, arbitrary request serialization, or role snapshots. A rejected/no-op command records no successful lifecycle audit event.

12. After the target mutation and audit insert have flushed successfully, revoke every tracked local authenticated session for that target account before allowing the database transaction to complete. Apply this to both disable and enable transitions so no stale tracked session survives a security boundary. Do not revoke the administrator or unrelated accounts unless that account is the target.

13. Session-revocation failure must fail closed and roll back the lifecycle mutation and audit. If a later database commit fails after sessions have already been expired, the database retains its preceding lifecycle state while affected sessions may remain expired; document and test this safe non-atomic asymmetry.

14. Prove both race orderings for disablement against session registration. If registration completes first, the lifecycle command must see/revoke that tracked session. If disablement obtains the account lock first, the login must fail final registration. Also prove that a pre-disable authentication cannot become a usable session after a rapid disable→enable transition because its authentication generation is stale.

15. Focused tests must prove authorization, actor derivation, stable-public-ID targeting, self-disable denial, missing/no-op handling, state preservation, enable lock-state clearing, generation advancement, ordinary-login generation stability, bounded failures, audit contents/order, session-revocation ordering, rollback behavior, and absence of secret/session material.

16. Real-MySQL and HTTP integration verification must prove disablement blocks new authentication, expires all previously authenticated sessions for the target, preserves unrelated sessions, and permits authentication with the unchanged credential only after explicit re-enable. It must deterministically cover in-flight authentication/session-registration races without sleep-based timing.

17. Existing password-change behavior must remain correct with the new authentication generation. Old-password rejection, new-password authentication, stale authentication rejection, session fixation, unlimited concurrent-session behavior, 30-minute default idle timeout, CSRF, logout, account creation, first-administrator provisioning, persisted authority derivation, audit, Flyway, and architecture regressions remain green.

18. Migration verification must prove V1–V6 are unchanged, V7 upgrades an existing V6 database successfully, existing accounts receive a valid generation, clean migration reaches the same final schema, Flyway validation passes, and no production identity/security data is seeded.

19. Update only applicable mutable module, migration, TASK, IMP, implementation-state, and routing documentation with verified facts. Do not edit frozen planning sources.

20. Completion requires required local verification, exact-final-head policy/Linux/Windows CI, clean trusted-main gates, protected PR integration, and successful push CI on the actual implementation merge SHA.

## Implementation behavior

AccountLifecycleService exposes explicit enable/disable commands accepting only a target
public UUID. CurrentActor requires identity:admin and supplies the actor UUID. Self-disable,
missing targets and no-op transitions are rejected before mutation or revocation. Infrastructure
failures expose fixed reasons without their causes. Each standalone command uses a 15-second
REQUIRES_NEW READ COMMITTED transaction, public-ID row lock and explicit managed-entity refresh.

V7 adds a non-secret BIGINT authentication_generation with default zero and a nonnegative
constraint. Password replacement and each lifecycle transition increment it without wraparound;
ordinary authentication bookkeeping leaves it unchanged. Credential timestamps now record the
actual Clock credential-change instant, even for repeated/fixed/backwards-clock replacements.
Lifecycle transitions preserve credential timestamps, credentials, canonical login, public ID,
roles and permissions. Enable clears failed-attempt and temporary-lock state.

Authentication captures the dedicated generation in request-only AuthenticationGeneration
metadata. Final registration refreshes/revalidates it under the same account lock, invokes the
standard servlet registration while locked, and strips metadata before context persistence.
The principal and durable session state are unchanged. Both registration orderings and a
pre-disable HTTP authentication resumed after disable then enable are tested with latches.

Exactly one IDENTITY_ACCOUNT_ENABLED or IDENTITY_ACCOUNT_DISABLED event records CurrentActor's
public UUID, target type IDENTITY_ACCOUNT, target UUID, null reason and fixed
administrative-account-lifecycle context. Both mutation and audit flush before target expiry.
Revocation failure rolls back database state/audit. A failure at later commit can leave sessions
expired with the preceding database state retained; both directions are tested. This safe
asymmetry requires fresh authentication and does not grant a disabled account access.

No production adapter, assignment administration, Worker coupling, new infrastructure,
dependency, deployable, secret fixture or frozen-planning change is introduced.
