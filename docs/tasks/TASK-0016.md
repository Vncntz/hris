# TASK-0016 — Establish the Agency/platform root

Status: PLANNED; implementation gate pending

Parent implementation item: [IMP-012](../implementation/tasks/IMP-012.md)

This is a planning work order. Implementation may begin only after this planning PR merges through protected `main` and `ci / policy`, `ci / build-linux`, and `ci / build-windows` pass on its exact merge SHA. A later explicit implementation instruction is required. Do not implement Agency code in this planning PR.

## Goal and authority

Create the smallest durable, module-owned Agency configuration/business root for one installation and one database. [IMP-012](../implementation/tasks/IMP-012.md) records the verified predecessor and frozen-plan authority. In particular, D-081 rules out SaaS-style tenancy keys; D-109/D-110 require module boundaries; D-111/D-112 govern normal aggregate persistence and transactions; D-132 excludes real customer data; D-147/D-148 require executable checks and completed verification. No approved ADR applies.

## Current baseline

`platform-operations` has the append-only audit implementation but no Agency root. The global Flyway stream in `hris-app` has V1–V3. `shared-kernel` supplies neutral public-ID/time primitives. Identity & Access exposes `CurrentActor` and basic security but later role/permission administration belongs to IMP-013. Normal Maven verification includes eight architecture tests and an all-15-production-module classpath guard. The standalone synthetic-data tool remains outside that guard.

## Implementation direction

1. Refresh `main` and verify the planning PR's exact-merge-SHA post-merge CI before editing. Reconcile any newer main state. Keep implementation in the `platform-operations` ownership boundary, with only necessary app wiring and global migration changes.
2. Model one Agency root with a stable public identifier and a minimal human-readable agency name. Keep its JPA entity and repository module-internal. Expose narrow application command and read contracts for later modules; do not expose the entity as a cross-module API.
3. Provide explicit initial creation and controlled name update. Reject invalid names and duplicate creation. Make concurrent creation unable to persist a second Agency by using a database-enforced singleton invariant, with clear application-level failure behavior. No customer-specific or vendor-known default Agency is seeded.
4. Protect mutation through the existing authenticated-actor/authorization boundary. Do not invent a permanent bootstrap bypass or a new role-management system. If secure initial provisioning cannot be completed with the existing contract without an operator decision, stop and report that decision before implementing a weaker path.
5. Preserve the existing append-only audit convention for successful creation and changes, without logging secrets or personal data. Use short transaction boundaries and the repository's public-ID and UTC conventions.
6. Add the next available **global** Flyway migration after refreshing `main`. At the current planning baseline this would be V4; resolve any concurrent version allocation against the then-current main before implementation. Preserve V1–V3 unchanged. Do not insert a real or sample Agency in the migration.
7. Add focused unit and real-MySQL integration tests for first creation, subsequent creation rejection, concurrency/singleton enforcement, read/update behavior, authorization, audit evidence, and Flyway migration/restart persistence. Keep the architecture suite and its module-coverage guard intact. Document the public boundary, setup behavior, and deferred configuration surface.

## Non-goals

No SaaS or multi-agency tenancy framework; no agency ID on unrelated aggregates; no broad settings registry; no role/permission administration (IMP-013); no Client/Site (IMP-014); no licensing, health, backup, upgrade, payroll, statutory rules, or UI administration. Do not add a production marker solely to satisfy architecture tests. Do not change protected-main settings or frozen planning sources.

## Acceptance criteria

1. The planning predecessor gate is verified on its exact merge SHA and current `main` is reconciled.
2. Exactly one durable Agency can exist per installation/database, including under concurrent creation attempts. A duplicate attempt fails clearly and does not alter the existing root.
3. Agency has a stable public identifier separate from any internal relational key; the name is validated. Persistence is owned by Platform Operations and the JPA entity/repository are not public cross-module contracts.
4. Creation and update require the defined authorization boundary; unauthenticated or unauthorized mutation fails. No seeded production Agency, default credential, or permanent bypass exists.
5. Successful mutation creates the intended append-only audit evidence. Failed mutation has no misleading success audit event.
6. The next global Flyway migration creates only this task's necessary schema and constraints. Existing released migrations are untouched. Real-MySQL tests verify migration, data integrity, and restart persistence.
7. All eight existing architecture tests and the 15-module completeness guard remain present and pass. No new prohibited infrastructure or unrelated production capability is introduced.
8. Relevant module documentation explains setup, the application/query boundary, and deferred fields. No real customer data or secrets appear in code, fixtures, logs, or CI artifacts.
9. Required local checks and exact-final-head PR `ci / policy`, `ci / build-linux`, and `ci / build-windows` pass. Trusted-main integration gates and exact-merge-SHA post-merge `push` CI pass before this task is complete.

## Security, privacy, audit, migration, and deployment

The Agency name is operational configuration; avoid real customer values in development and CI. Authorization and audit are required for mutation. The schema change uses the one application Flyway stream and normal upgrade validation; it adds no new deployable service or external dependency. No statutory formula, rate, deadline, or form is part of this task.
