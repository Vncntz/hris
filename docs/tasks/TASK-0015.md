# TASK-0015 — Harden architecture-test production-module coverage

Status: PLANNED

Parent implementation item: [IMP-011](../implementation/tasks/IMP-011.md)

This work order follows the verified completion of TASK-0014. Implementation begins only after the planning PR containing the TASK-0014 closeout and this TASK-0015 work order has merged to protected `main` and required post-merge `push` CI has passed on that planning merge SHA.

## Goal

Close the remaining IMP-011 architecture-test coverage gap by making normal Maven verification fail when an expected production module silently disappears from the architecture-test scope.

TASK-0014 successfully established executable modular-monolith rules, but its import-coverage test currently proves only representative Identity & Access and Platform/Operations classes are visible. A production module whose dependency disappears from the `hris-app` architecture-test classpath can therefore escape the remaining ArchUnit rules.

TASK-0015 must make architecture-test scope completeness itself executable.

## Implementation direction

1. Refresh `main` and verify the predecessor and planning gates.

2. Preserve all seven existing TASK-0014 architecture checks.

3. Add an explicit executable completeness guard for the current production modular-monolith module set.

   The guard must ensure that normal Maven verification cannot silently succeed after an expected application/business module disappears from the architecture-test scope.

4. Prefer the smallest stable implementation.

   An explicit expected package/module manifest in the architecture test is acceptable. A build/POM-level assertion is also acceptable when that proves classpath completeness more reliably.

   Do not add a general build-analysis framework.

5. Cover the current production application scope, including the business/application modules and `shared-kernel`, while intentionally excluding the standalone `tools/synthetic-data` build tool.

6. Do not rely solely on the existing representative `AccountEntity`, `AuditEventEntity`, and `AccountRepository` assertions.

7. Avoid introducing production classes merely so tests have a marker to find.

   If placeholder-module `package-info` output cannot be used reliably, choose a test/build-level mechanism that proves module presence without polluting production code.

8. Add a negative-control verification.

   During local verification, temporarily remove or otherwise exclude one representative currently expected `hris-app` production-module dependency such as `reporting`, confirm the new guard fails for the intended reason, restore the dependency, and rerun verification cleanly.

   The temporary mutation must not remain in the final diff.

9. Keep failure output explicit.

   A missing module should identify the missing expected module/package rather than fail with an unrelated ArchUnit error.

10. Update `docs/architecture/EXECUTABLE_RULES.md` to state that architecture-test scope completeness is mechanically protected and that the standalone synthetic-data tool remains intentionally outside this application-classpath rule.
