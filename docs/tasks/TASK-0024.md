# TASK-0024 - Authenticated account creation boundary

Status: PLANNED - documentation planning only; implementation requires a separate explicit operator instruction.

Parent implementation item: [IMP-013](../implementation/tasks/IMP-013.md)

## Goal and scope

Add an authenticated Identity & Access application-service boundary for an administrator with `identity:admin` to create an ordinary account and its initial adaptive credential. The new account starts enabled under the existing constructor behavior, with zero assigned roles and zero authorities. Creation must never imply administrative privilege. Successful creation and privacy-minimized audit evidence commit atomically.

Identity & Access owns the service, validation, credentials and persistence. Reuse `CurrentActor`, the existing PasswordEncoder and shared-kernel `AuditRecorder`; Platform/Operations owns audit persistence and the application composes dependencies. Expose only stable public account UUIDs and non-secret results, never module-owned entities/repositories. User identity remains separate from Worker identity.

## Acceptance criteria for later implementation

1. Every creation invocation requires an authenticated account public ID and `CurrentActor.requireAuthority("identity:admin")` at the application-service boundary. Reject absent/anonymous authentication, unsupported principals and authenticated callers lacking the authority before hashing or persistent mutation. Derive the actor exclusively from CurrentActor; accept no caller-supplied actor override. Authority comes from explicit authenticated assignments, never a login or role-name shortcut. This service is composed for normal authenticated application use without an anonymous HTTP route or local bootstrap bypass.

2. Reuse existing canonical-login rules and the database uniqueness constraint. Create an independently generated stable public UUID and one enabled account with initial credential/security timestamps, zero failure count and no temporary lock. Accept no enabled-state, role, permission, assignment or privilege parameter. Create no role, permission or membership row; do not alter the creator's assignments, existing accounts or bootstrap state. The account can authenticate with zero authorities and cannot pass identity:admin enforcement.

3. Use the existing adaptive Argon2id delegating encoder and existing password-validation behavior: default minimum 12 and bounded maximum 128 Unicode code points, malformed Unicode rejection, confirmation matching and no trimming, case folding or truncation. Prefer a reusable Identity-owned credential helper if needed rather than coupling normal creation to the bootstrap provisioner. Hash outside database locks and retain only the encoding. Take ownership of mutable password/confirmation buffers and clear them on every exit path, including denial, validation and persistence failure. Keep unavoidable encoder copies short-lived. Secret-bearing inputs must have no printable serialization/toString; results and exceptions contain neither plaintext nor hashes. Production cost calibration and configurable policy qualification remain later hardening obligations.

4. A short transaction commits the new account and exactly one `IDENTITY_ACCOUNT_CREATED` audit event together through AuditRecorder. Use the authenticated creator's public UUID as actor, `IDENTITY_ACCOUNT` as target type and the new public UUID as target, with fixed non-secret creation context. Do not audit login, password, hash, request serialization or arbitrary user-supplied context. Audit failure rolls back creation. No failed request may produce a success audit event or partial account.

5. Canonically duplicate logins, including competing concurrent requests, cannot create duplicate accounts or successful duplicate audit events. Retain database-enforced uniqueness as the final authority and return bounded non-secret failure information after rollback. Do not overwrite, adopt, reset or elevate an existing principal. Real-MySQL concurrency tests use deterministic coordination and prove one committed account/event pair for competing same-canonical-login requests.

6. Focused unit tests prove authorization denial before encoder/write/audit use, authenticated actor derivation, canonical input and credential bounds/confirmation/Unicode checks, secret-buffer clearing on success and every failure category, and non-secret result/failure behavior. Real-MySQL tests prove authorized creation, normal authentication with zero authorities, absence of memberships/privilege propagation, uniqueness/duplicate rollback, concurrent duplicate creation and atomic audit-failure rollback. Exercise the production service with real CurrentActor/authentication integration, including anonymous and no-authority denial, rather than relying solely on mocked authorization.

7. Keep bootstrap durable closure and existing account/authentication, lockout, authority filtering, session, CSRF, audit, migration and architecture regressions green. Prove creation leaves V6 completion state and existing identity/audit records intact. Use only generated ephemeral synthetic credentials and data, with no reusable credential literal or secret in logs/reports/fixtures.

8. Update applicable mutable module, TASK, IMP and implementation-state records with actual behavior and verification. Complete only after required local checks, exact-final-head CI, clean trusted-main gates, protected merge and successful push CI on the actual implementation merge SHA. This planning PR satisfies none of the implementation acceptance criteria by itself.
