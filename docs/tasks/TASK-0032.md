Fresh post-merge review found a security defect in `CredentialReauthenticationService`: [PR #55 review finding](https://github.com/Vncntz/hris/pull/55#discussion_r4171478811) notes that recent credential re-authentication does not enforce the Account's temporary lock and wrong re-authentication credentials do not participate in the existing bounded failed-attempt/lockout policy.

The merged implementation confirms the finding. `CredentialReauthenticationService` verifies an enabled-account password hash and later checks enabled state plus unchanged credential state, but it neither checks `AccountEntity.isLockedAt(...)` nor records a failed authentication attempt. Its current unit coverage preserves failure/lock state during successful proof using an expired temporary-lock fixture; that test does not itself prove active-lock acceptance. The service has no active-lock check, so active locks are also bypassed.

## Goal

Make recent credential re-authentication participate in the same bounded failed-authentication and temporary-lock policy already used by normal password authentication.

An active temporary Account lock must prevent recent privileged credential proof even when the supplied password is correct.

A wrong recent-re-authentication credential must contribute to the repository-managed failed-attempt counter and establish the configured temporary lock at the configured threshold.

The correction must preserve TASK-0029's session-local proof isolation, stale-credential protection, authority ordering, transaction boundaries, audit behavior, credential hygiene, and existing session-revocation behavior.

## Current implementation baseline

Current `main` provides:

- adaptive Argon2id password authentication;
- configurable failed-attempt threshold and temporary lock duration;
- `AccountEntity.isLockedAt`, `clearExpiredLock`, `recordFailure`, and `recordSuccess`;
- normal authentication that enforces temporary lock state and failed-attempt bookkeeping;
- recent credential re-authentication through `CredentialReauthenticationService`;
- a bounded `REQUIRES_NEW`, `READ_COMMITTED` post-hash Account recheck;
- per-session proof clearing and publication through `RecentAuthenticationSession`;
- recent-proof guards on all eleven existing Identity administrative mutations;
- generation-based stale-authentication protection and targeted local session expiry.

The defect is limited to the recent-re-authentication credential path: it currently treats lock/failure security state as immutable and therefore bypasses the common Account lockout policy.

## Acceptance criteria

1. Preserve `CurrentActor.requireUserId()` as the sole source of the Account being re-authenticated. Do not accept an Account UUID or login name from the caller.

2. Preserve the owned mutable credential-buffer contract and clear the supplied password buffer on every success and failure path.

3. Preserve `RecentAuthenticationSession.attempt(...)` semantics: beginning an explicit attempt clears prior proof and failed verification never leaves a usable marker.

4. Use the existing repository-managed `PasswordEncoder`. Do not introduce another password representation or comparison mechanism.

5. Use the existing `SecurityPolicy.maxFailedAttempts()` and `SecurityPolicy.lockDuration()` values. Do not create an independent re-authentication threshold or lock duration.

6. Refuse a caller-held database transaction before adaptive credential work, preserving TASK-0029's rule that password hashing/comparison must not execute while an unrelated caller transaction holds locks.

7. Missing or disabled Accounts must continue to fail closed with bounded non-secret outcomes.

8. An Account already under an active temporary lock must not establish recent-authentication proof even when the supplied password is correct.

9. Where an unlocked/locked scalar snapshot can safely avoid unnecessary adaptive password work, an already-observed active lock should fail before expensive verification. The later locked transaction remains authoritative for races.

10. Adaptive password comparison must continue outside the Account mutation lock.

11. After password comparison, use a short bounded `REQUIRES_NEW`, `READ_COMMITTED` transaction and the existing pessimistic Account locking/managed-entity refresh convention before either publishing proof or committing failed-attempt bookkeeping.

12. Under the Account lock, recheck at least Account existence, enabled state, exact credential encoding used for the adaptive comparison, and current temporary-lock state.

13. A credential changed concurrently after the pre-hash snapshot must fail as stale and must never establish proof.

14. A wrong credential checked against an unchanged current encoding must record exactly one failed authentication attempt.

15. Failed re-authentication bookkeeping must use the same Account failure/lock semantics as normal authentication.

16. Reaching the configured failed-attempt threshold through recent re-authentication must establish the configured temporary lock.

17. Concurrent failed re-authentication attempts from separate sessions must not lose increments or bypass the threshold; Account-row serialization must preserve deterministic bounded state.

18. If the Account becomes locked between the initial snapshot and the locked recheck, proof must be rejected even if the credential matched the earlier snapshot.

19. Wrong-credential bookkeeping must commit before the caller receives the credential-rejected outcome. Do not throw from inside the transaction in a way that rolls back the required failure count.

20. A database/commit failure while attempting to record a failed credential must expose only the bounded persistence failure and must not publish proof.

21. Successful re-authentication after an expired lock must use security-bookkeeping semantics consistent with normal Account authentication. Failed-attempt/expired-lock state must not remain in a misleading near-threshold condition after a successful credential proof.

22. Security bookkeeping may update only fields required by the existing authentication failure/success policy, such as failure count, lock expiry, security timestamp, and normal JPA row version.

23. Re-authentication must not change the password hash, credential-update timestamp, enabled state, Account authentication generation, Role generations, role membership, permission membership, public UUID, canonical login, or business audit history except where an independently existing Account method necessarily updates the permitted authentication bookkeeping.

24. No business audit event is required solely for successful or failed credential proof. Existing Identity administrative mutation audit events remain unchanged.

25. Lockout enforcement must not grant authority, replace `identity:admin`, or alter authorization-before-proof ordering.

26. A lock caused by ordinary login failures must also prevent recent re-authentication in an already-existing authenticated session.

27. A lock caused by recent re-authentication failures must also be honored by the ordinary login path until normal lock expiry/recovery semantics permit authentication again.

28. Do not introduce automatic local-session revocation merely because a re-authentication attempt triggers account lockout; session revocation behavior remains separately governed by the existing lifecycle, password-change, and authority-generation rules.

29. Existing targeted session revocation must continue to make prior proof unusable.

30. Existing cross-session recent-proof isolation, exact freshness expiry, clock-rollback rejection, logout/new-login clearing, stale-password races, and CSRF/session-fixation protections must remain green.

31. Credential, password hash, session identifier, authentication token, and other private security values must not enter logs, audit context, exception causes/messages, committed fixtures, or documentation.

32. No new distributed session store, Redis, queue, messaging system, microservice, or external authentication service may be introduced.

33. No Flyway migration is expected. Released V1–V8 must remain byte-for-byte unchanged.

34. No new cryptography or authentication dependency is expected.

35. Unit tests must cover active-lock rejection, pre-hash lock short-circuit where implemented, wrong-credential increment, threshold lock creation, successful post-expiry recovery, stale-credential race, persistence/commit failure, buffer clearing, and bounded failures.

36. Replace the current unit assertion that deliberately permits successful proof while temporarily locked. Tests must prove the corrected security contract rather than preserve the defect.

37. Real-MySQL/HTTP coverage must prove at least:
    - repeated wrong re-authentication attempts increment persisted failed-attempt state;
    - the configured threshold establishes a real temporary lock;
    - a correct re-authentication credential cannot establish proof while that lock is active;
    - an active lock established through ordinary authentication failures also blocks proof in an already-authenticated session;
    - lockout established by re-authentication is honored by ordinary login;
    - expiry followed by successful proof restores normal usable state according to the common authentication policy;
    - concurrent wrong attempts from distinct sessions do not lose increments;
    - no failed attempt leaves earlier proof usable;
    - successful proof still permits the protected administrative command only when `identity:admin` is present.

38. Existing AccountAuthenticationIT, CredentialReauthenticationIT, PasswordChangeIT, AccountLifecycleIT, AccountRoleAssignmentIT, RoleAdministrationIT, first-administrator, authorization, migration, audit, architecture, session, CSRF and logout regressions must remain green.

39. Update mutable TASK/IMP/state/routing and Identity module documentation with verified final behavior.

40. Completion requires required local verification, exact-final-head policy/Linux/Windows CI, clean trusted-main Git Integration Agent gates, protected PR integration, and successful policy/Linux/Windows `push` CI on the actual implementation merge SHA.

## Security, privacy, and audit implications

The correction closes a credential-guessing bypass available to an attacker who already possesses a valid privileged HTTP session.

The existing account-level bounded authentication policy becomes authoritative for both ordinary password login and explicit recent credential proof.

Credential values remain ephemeral and session proof remains non-secret.

Authentication failure/success bookkeeping is security state, not a business administrative mutation, so no new append-only business audit event is introduced.
