## Goal

Provide an authenticated Identity & Access application-service boundary for adding and removing existing Role assignments on existing Accounts while ensuring every committed membership change invalidates stale authenticated authority snapshots and in-flight authentication for the affected account.

This task administers **Account-to-Role membership only**.

It does not create, rename, enable, disable, delete, or change permissions on Roles.

## Current implementation baseline

V5 already owns normalized Identity & Access persistence for:

- `identity_role`;
- `identity_permission`;
- `identity_account_role`;
- `identity_role_permission`.

`RoleEntity` has a stable public UUID, canonical name, enabled state, version, and permissions.

`AccountEntity` owns its role set. The existing ordinary authentication path loads assigned enabled roles and their permission keys and copies the resulting deduplicated authorities into the authenticated Spring Security token.

Authorities remain session snapshots.

TASK-0026 added `identity_account.authentication_generation`. Password replacement and account lifecycle transitions advance that generation; ordinary authentication bookkeeping does not. Final servlet-session registration locks and refreshes the account and rejects authentication carrying a stale generation.

`AuthenticatedSessionRevoker.revoke(UUID)` expires all locally tracked authenticated sessions belonging to one account public UUID.

No ordinary administrative account-role assignment service currently exists. Account-role membership is currently written only by the controlled first-administrator bootstrap path.

No approved ADR changes this direction.

## Acceptance criteria

1. Add an authenticated Identity & Access application-service boundary for explicit Account-to-Role assignment and removal. A recommended shape is `AccountRoleAssignmentService.assign(UUID accountPublicId, UUID rolePublicId)` and `remove(UUID accountPublicId, UUID rolePublicId)` or an equivalently narrow command API.

2. Every command must first require `CurrentActor.requireAuthority("identity:admin")` and derive the audit actor exclusively from `CurrentActor.requireUserId()`. No actor identifier supplied by the caller may influence authorization or audit attribution.

3. Accept only the target Account stable public UUID, Role stable public UUID, and the explicit assignment/removal operation. Do not accept account login text, role canonical name, permission key, Worker identifier, actor override, authority shortcut, arbitrary audit context, credential, or session identifier.

4. Missing Accounts, missing Roles, unsupported/unauthenticated callers, authorization failures, duplicate assignment, missing membership, disabled-Role assignment attempts, persistence failure, audit failure, and session-revocation failure must produce bounded non-secret outcomes. Do not expose SQL, internal relational IDs, account login text, credentials/hashes, session identifiers, or internal exception causes.

5. Adding an already-assigned Role and removing a Role that is not assigned are rejected as explicit no-op outcomes. They must not advance authentication generation, write a successful assignment audit event, or revoke sessions.

6. Assigning a disabled Role is rejected. Removing an already-existing assignment to a disabled Role remains permitted so obsolete memberships can be cleaned up without first re-enabling the Role.

7. Execute each mutation in a short standalone `REQUIRES_NEW`, READ COMMITTED transaction using the repository's established timeout/conventions. Lock the target Account by stable public UUID and explicitly refresh the managed Account under that lock before checking or mutating membership. Do not blindly retry business-validation failures.

8. Use the existing V5 `identity_account_role` relation. Do not duplicate account-role membership in another table, cache, configuration source, or module.

9. Every committed Account-to-Role membership change must advance the affected Account's authentication generation exactly once in the same database transaction as the membership mutation. Missing/no-op/rejected commands must not advance it.

10. Membership mutation must preserve the Account public UUID, canonical login, enabled state, password encoding, credential-update timestamp, failed-login/temporary-lock state, unrelated Role assignments, and all unrelated Identity state.

11. Self-directed membership changes are permitted only when they cannot remove the caller's effective `identity:admin` authority. If the authenticated administrator removes one of its own Role assignments, calculate the resulting enabled Role/Permission set and reject the command before mutation when `identity:admin` would no longer be present. This protects the authenticated administrative path without imposing unnecessary dual-control on harmless self changes.

12. Record exactly one privacy-minimized audit event for each committed membership change:
   - assignment: `IDENTITY_ACCOUNT_ROLE_ASSIGNED`;
   - removal: `IDENTITY_ACCOUNT_ROLE_REMOVED`;
   - target type: `IDENTITY_ACCOUNT_ROLE`;
   - target reference: canonical `<account-public-uuid>/<role-public-uuid>`;
   - actor: authenticated administrator public UUID;
   - reason: `null`;
   - context: fixed `administrative-account-role-assignment`.

13. Do not audit login text, Role name, Permission snapshots, credentials/hashes, session identifiers, arbitrary request serialization, or internal database IDs. Rejected/no-op operations record no successful membership-change event.

14. Flush the Account membership/generation mutation and its audit insert successfully before expiring sessions. Then revoke every tracked local authenticated session for the affected Account before transaction completion. Do not revoke unrelated Accounts.

15. Session-revocation failure must fail closed and roll back the membership mutation, authentication-generation change, and audit event. If a later database commit fails after sessions have been expired, the database may retain its preceding assignment state while sessions remain expired; document and test this safe non-atomic asymmetry.

16. Deterministically prove both relevant ordering classes against final session registration. Authentication completed against the old assignment generation must never become a usable post-change session. If registration finishes first, assignment mutation must see and revoke that session; if assignment mutation owns the Account lock first, stale final registration must be rejected by authentication generation.

17. After assigning an enabled Role, the affected Account must obtain that Role's persisted authorities only after fresh authentication. After removing a Role, all old sessions must be expired and fresh authentication must no longer contain authorities supplied solely by that Role. Unrelated Account sessions and authorities remain unchanged.

18. Focused unit tests must cover authorization, actor derivation, stable-public-ID targeting, missing Account/Role, disabled Role assignment, duplicate/missing membership, membership preservation, generation advancement, no-op generation stability, self-admin protection, bounded failures, exact audit contents/order, revocation ordering, rollback behavior, and absence of secret/session material.

19. Real-MySQL and real-HTTP integration verification must cover at least:
   - assigning the existing administrator Role to an ordinary synthetic Account;
   - forced expiry of that Account's existing sessions;
   - fresh authentication acquiring `identity:admin`;
   - removing that assignment;
   - expiry of every affected tracked session;
   - fresh authentication no longer having `identity:admin`;
   - preservation of unrelated authenticated sessions;
   - deterministic stale-authentication/final-registration races;
   - transaction rollback on audit/revocation failure where applicable.

20. No schema migration is expected. Released V1 through V7 must remain byte-for-byte unchanged. Flyway validation and the existing clean/upgrade migration regression suite must remain green. Do not seed Accounts, Roles, Permissions, assignments, credentials, customer data, or other production security state.

21. Account creation, first-administrator provisioning, password change, account lifecycle, authentication-generation behavior, session fixation, unlimited concurrent-session semantics, the 30-minute default idle timeout, CSRF, logout, persisted authority loading, audit, architecture tests, and existing MySQL tests must remain green.

22. Update only applicable mutable Identity module documentation, TASK/IMP/state/routing documentation, and test records with verified facts. Do not edit frozen planning sources.

## Security, privacy, and audit implications

Authorization is enforced at the application-service boundary and not delegated to UI visibility.

The authenticated actor comes only from `CurrentActor`.

Stable public UUIDs are the only cross-boundary Account/Role identifiers.

Membership changes are security-boundary mutations. Existing authenticated authorities are snapshots and therefore require explicit generation invalidation and local-session expiry.

Audit data must remain privacy-minimized and contain no credentials, login text, Role names, permission dumps, or session identifiers.

Synthetic values only may be used in source, tests, logs, task records, or CI evidence.

## Implementation behavior

AccountRoleAssignmentService.assign/remove accepts only Account and Role public UUIDs.
CurrentActor first requires identity:admin and supplies the audit actor. Explicit missing,
duplicate, absent-membership, disabled-assignment and self-admin-removal outcomes precede
mutation. Removing obsolete disabled-Role memberships remains allowed. Self-removal
checks the remaining persisted enabled Roles' permissions, refreshing managed Roles
before evaluating effective identity:admin; harmless self changes revoke the actor's sessions.

Each standalone command uses a 15-second REQUIRES_NEW READ COMMITTED transaction,
locks and refreshes the Account and reuses V5 membership. Each mutation advances V7's
authentication generation once without wraparound. Credentials, security timestamps,
failed attempts/locks, enabled state, identity, unrelated memberships and Role/Permission
state are preserved. No migration, seed or dependency is added; released V1-V7 are unchanged.

Exactly one IDENTITY_ACCOUNT_ROLE_ASSIGNED/REMOVED audit event has the CurrentActor UUID,
IDENTITY_ACCOUNT_ROLE target type, canonical account/role UUID reference, null reason,
and fixed administrative-account-role-assignment context. The shared persistence flush
covers membership, generation and audit before every target session is expired. Revocation
failure rolls back all database writes. A later commit failure may retain preceding
membership while sessions remain expired; fresh authentication uses that preceding state.
This safe asymmetry is tested in both directions. Other accounts' sessions remain intact.

The existing locked final-registration generation check rejects authentication captured
before a membership change. Latch-coordinated real HTTP/MySQL tests prove mutation-first
and registration-first orderings for both commands, plus assign/remove generation reuse
prevention. The test adapter is absent from production; no UI or REST boundary is added.
IMP-013 remains ACTIVE; no TASK-0028 is allocated and IMP-014 is not started.
