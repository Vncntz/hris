## Goal

Add the smallest useful executable architecture-test foundation that makes key modular-monolith boundaries fail normal Maven/CI verification instead of relying solely on documentation and review.

The task must establish mechanical protection for:

- dependency cycles between application/module packages;
- cross-module exposure of JPA entities;
- cross-module exposure of Spring Data repositories;
- reverse dependencies from `shared-kernel` into business/application code;
- business-module dependencies on the application/UI composition layer;
- Vaadin leakage into business modules;
- casual introduction of currently prohibited Kafka/Redis infrastructure dependencies.

Rules that cannot yet be expressed without inventing future domain/package structure must remain documented review obligations rather than speculative implementation.

## Implementation direction

1. Refresh `main` and verify the predecessor and planning gates before editing.

2. Use the existing `hris-app` test source set as the architecture-test host.

   `hris-app` already acts as the composition root and has application-module visibility. Do not add an additional reactor module merely to host ArchUnit unless this approach demonstrably cannot inspect the required production classes.

3. Add ArchUnit as a test-only dependency.

   Use:

   `com.tngtech.archunit:archunit`

   Pin version `1.5.1` through normal root dependency/version management.

   Use ordinary JUnit tests. Do not add the ArchUnit JUnit-specific engine unless a concrete technical requirement appears.

4. Import production classes only.

   Exclude test classes from architecture analysis so integration/unit-test dependencies do not masquerade as production architecture.

5. Add an executable cycle rule.

   Production module/package slices under `io.github.vncntz.hris` must be free of dependency cycles.

   The composition root may depend inward on modules; business modules must not form reverse cycles through it.

6. Keep JPA entities module-internal.

   Classes annotated as JPA entities must not be public cross-module contracts.

   The rule must pass for the existing `AccountEntity` and `AuditEventEntity`.

7. Keep Spring Data repositories module-internal.

   Spring Data repository types must not be public contracts accessible as another module's persistence API.

   Prefer checking repository assignability rather than relying only on a class-name suffix if ArchUnit supports this cleanly.

8. Protect `shared-kernel`.

   `io.github.vncntz.hris.sharedkernel..` must not depend on business-module packages or the `hris-app` application/composition layer.

   The current JDK-oriented neutral kernel must remain neutral.

   Do not attempt semantic classification of every future type; mechanically enforce the dependency direction that is currently provable.

9. Protect the composition/UI boundary.

   Business/module packages must not depend on `io.github.vncntz.hris.app..`.

   Production business/module code must not depend on Vaadin UI types.

   The application/composition root remains allowed to depend inward on business modules.

10. Guard prohibited infrastructure dependencies.

    Extend the existing Maven Enforcer configuration with a narrowly documented dependency rule that prevents casual introduction of the currently prohibited Kafka/Redis dependency families.

    Cover the obvious Kafka/Spring-Kafka and Redis/Lettuce/Jedis/Spring-Data-Redis families.

    The rule must be easy to intentionally revise later only through an approved architecture decision/task; do not create a generalized dependency-policy framework.

11. Do not pretend to enforce future contracts that do not exist.

    In particular, D-110's distinction between target-module application commands and query contracts cannot yet be fully proven across placeholder modules.

    Document that boundary as still mandatory in review until concrete packages/contracts permit a stable mechanical rule.

12. Keep failure output useful.

    Architecture-test names and rule descriptions should identify the violated architectural intent instead of exposing only a low-level predicate.

13. Normal Maven verification must execute the rules.

    Do not add a bespoke workflow job if normal reactor `test` / `verify` already executes them.

14. Add concise mutable documentation describing:

    - where architecture tests live;
    - which rules are executable;
    - which rules remain review-only;
    - how a future approved dependency/boundary change should update the tests in the same task;
    - that architecture tests are build/test-only and add no production runtime component.

## Acceptance criteria

1. ArchUnit core is pinned and test-scoped; no production module obtains a runtime ArchUnit dependency.

2. Architecture tests execute automatically under ordinary Maven `test` / `verify`.

3. Production test import excludes test classes.

4. An executable architecture rule rejects cyclic module/package dependencies.

5. JPA entity classes are required to remain non-public/module-internal.

6. Spring Data repository types are required to remain non-public/module-internal.

7. `shared-kernel` is prevented from depending on business/application packages.

8. Business/module packages are prevented from depending on the `hris-app` application/composition package.

9. Vaadin production dependencies are prevented from leaking into business modules.

10. Maven-level enforcement prevents casual introduction of the currently prohibited Kafka/Redis infrastructure dependency families.

11. Existing production code passes the rules without a speculative package/module refactor.

12. No new reactor module is introduced solely for architecture tests unless the preferred `hris-app` approach is proven technically unsuitable and that deviation is documented.

13. No JPMS, Spring Modulith, microservice, broker, Redis service, or other distributed-infrastructure architecture is introduced.

14. No business-domain behavior, authentication behavior, audit behavior, synthetic-data behavior, payroll/compliance behavior, or persistence schema changes.

15. No Flyway migration is added or modified.

16. No real customer production data, credentials, secrets, private keys, or statutory values are added.

17. Architecture-rule documentation distinguishes mechanically enforced rules from future review-only obligations.

18. Frozen planning sources remain unchanged.

19. Required local verification passes with no unexpected skipped/failing tests.

20. Final implementation PR exact-head `ci / policy`, `ci / build-linux`, and `ci / build-windows` pass.

21. Protected-main integration succeeds through the trusted Git Integration Agent gates.
