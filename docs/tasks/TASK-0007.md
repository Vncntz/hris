# TASK-0007 — Real MySQL integration-test baseline

Status: LOCAL VERIFIED — PR CI and integration verification pending

Parent implementation item: [IMP-004](../implementation/tasks/IMP-004.md)

## Goal

Establish the smallest maintainable real-MySQL integration-testing foundation for the Maven modular monolith, using a supported MySQL 8.4 LTS-line container and Testcontainers or equivalent, without adding business schema or Flyway work.

The proving test should exercise Spring Boot datasource wiring and a real database connection, not invent business tables merely to demonstrate connectivity.

## Non-goals

- No Flyway migrations or migration conventions (IMP-005).
- No domain entities, JPA repositories, business tables, payroll/attendance/recruitment behavior, or application features.
- No configuration/secrets framework beyond the minimum isolated test wiring (IMP-007).
- No production MySQL installer/service packaging, backup/recovery, customer database configuration, or deployment automation.
- No synthetic-data generator implementation (IMP-010) and no real customer production data.
- No H2 compatibility claim or H2 substitute for MySQL semantics.
- No architecture-test implementation (IMP-011).
- No Docker Compose or persistent local development database unless a separate follow-up TASK under IMP-004 demonstrates a concrete need.

## Affected modules and files

Keep the implementation narrow. Expected candidates are:

- root pom.xml, only if shared dependency/plugin management is required;
- hris-app/pom.xml for application/test dependencies;
- hris-app/src/test/** and, if needed, hris-app/src/test/resources/** for reusable container bootstrap and the connectivity/wiring integration test;
- .github/workflows/ci.yml for the selected Ubuntu-only container-backed execution;
- root README.md or another existing developer entry point for ordinary Maven commands and prerequisites;
- this TASK, its parent IMP, task index, and mutable implementation state for verified completion evidence.

Do not modify hris-app/src/main/resources/application.properties or production runtime configuration merely for convenience. Change production-facing configuration only if the implementation proves it is the smallest correct baseline and document why.

## CI execution design

Use the existing CI topology rather than introducing a matrix or new infrastructure:

- keep ci / policy unchanged unless the implementation adds a directly relevant mechanical policy check;
- keep ci / build-windows on the ordinary full reactor clean verify path so Windows compilation, packaging, and non-containerized tests remain covered;
- make ci / build-linux execute the same reactor plus a dedicated Maven activation for the selected MySQL integration test, with mysql-it as the default planned profile name;
- do not run the same OS-neutral MySQL container test again on hosted Windows merely for symmetry;
- the MySQL integration activation must also be runnable locally through the Maven Wrapper on a machine with a compatible container runtime.

GitHub's current official Actions documentation lists both ubuntu-24.04 and windows-2025 as hosted runner labels, but documents Docker job/service containers as Linux-only on GitHub-hosted runners. This supports using Ubuntu for the container-backed database proof while preserving the existing Windows portability job:
- <https://docs.github.com/en/actions/reference/runners/github-hosted-runners>
- <https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers>

If Testcontainers' actual runtime requirements conflict with this simple design, stop and document the verified conflict rather than adding elaborate CI infrastructure.

## Version verification before implementation

Before adding or pinning dependencies, verify from authoritative official sources:

- current supported Testcontainers version/integration convention;
- exact supported MySQL 8.4 LTS-line container image tag/patch level;
- MySQL JDBC driver version when it is not supplied by Spring Boot dependency management;
- Spring Boot 4.1.x Testcontainers/service-connection conventions.

Prefer Spring Boot dependency management/BOMs where appropriate. Do not guess versions in the implementation.

## Acceptance criteria

TASK-0007 is complete only when all applicable criteria pass:

1. A focused automated integration test provisions a disposable real MySQL 8.4 LTS-line instance without manual database setup.
2. The test proves a real database connection and Spring datasource wiring without creating business schema, entities, repositories, or Flyway migrations.
3. MySQL/Testcontainers test dependencies and configuration are scoped narrowly and do not force unrelated modules to depend on database test infrastructure.
4. Test credentials/data are disposable and synthetic; no secret or customer production data is committed or logged.
5. The integration test is explicitly activated by the planned ordinary Maven Wrapper path and fails clearly when its required container runtime is unavailable; required tests are not silently skipped.
6. Ubuntu PR CI runs the selected MySQL integration test; Windows PR CI retains meaningful portability coverage without redundantly running the OS-neutral container test.
7. Existing non-database smoke/build verification remains valid; no production-inappropriate configuration is added merely to make tests pass.
8. Documentation states local prerequisites and exact commands, and mutable implementation state is updated only with evidence actually verified.
9. The baseline leaves IMP-005 able to add Flyway without replacing the container/bootstrap approach.
10. Frozen planning sources remain unchanged and the complete diff contains no later IMP/business scope.

## Security, privacy, and audit

Use ephemeral test credentials and synthetic data only. Never include real customer production data, reusable production credentials, or secrets in source, logs, fixtures, CI artifacts, or AI context. This task does not introduce application audit behavior.

## Migration and deployment

No production schema migration or Flyway work is authorized. No production MySQL service, installer, backup/recovery, or customer deployment change is authorized. The containerized MySQL instance is development/test infrastructure only.
