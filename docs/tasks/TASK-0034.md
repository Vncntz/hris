## Goal

Provide a controlled authenticated administrator operation for resetting another Account's password when that Account cannot perform the existing self-service current-password change.

The reset must preserve Identity & Access ownership, require `identity:admin` plus recent credential proof, replace only credential/security state, invalidate stale authentication, revoke tracked target sessions, and emit privacy-minimized transactional audit evidence.

## Relevant baseline and references

Current `main` is `c1717ea649e1fc6c9cca0bd2bae03a8406a927e1`.

`PasswordChangeService` already implements self-only current-password verification, adaptive replacement, authentication-generation advancement, lockout-state clearing, audit and local session revocation.

Administrative Account, membership and Role/Permission commands already require `identity:admin` followed by `RecentAuthenticationGuard`.

`AccountEntity.changePassword(...)` advances `authentication_generation`, replaces the encoding, updates credential/security timestamps and clears failed-attempt/temporary-lock state.

`AccountSessionRegistrationService` rejects authentication whose captured generation becomes stale before final session registration.

D-151 requires adaptive hashing, bounded authentication/session behavior and recent re-authentication for appropriate privileged operations. Password-cost hardware qualification and offline TOTP remain separate work.

## Scope and acceptance criteria

1. Add an Identity-owned administrative credential-reset application-service boundary accepting only a target Account public UUID plus owned mutable new-password and confirmation buffers.

2. Require `CurrentActor.requireAuthority("identity:admin")`, valid recent credential proof, and the authenticated administrator public UUID before target validation or mutation.

3. Reject null/invalid targets and reject resetting the caller's own credential through this administrative boundary. Self credential changes continue to use `PasswordChangeService`.

4. Reuse the existing Identity-owned password validation semantics, including current length and Unicode handling. Clear every supplied secret buffer on all success and failure paths.

5. Refuse an ambient caller transaction before adaptive hashing. Perform password encoding outside the database mutation transaction and outside target row locks.

6. Perform the mutation in a bounded `REQUIRES_NEW`, `READ_COMMITTED` transaction using the target Account row lock and managed-entity refresh before authoritative rechecks.

7. Resetting a disabled Account is permitted but must **not** enable it. Account identity, login, roles, permissions and lifecycle state remain unchanged.

8. Replace the password through the existing credential-state semantics: advance `authentication_generation`, update credential/security timestamps, clear failed attempts and temporary lock state, and preserve all unrelated Account state.

9. Commit exactly one `IDENTITY_PASSWORD_RESET` audit event with authenticated administrator UUID as actor and target Account UUID as target. Use a fixed non-sensitive context such as `administrative-password-reset`. Credential material, hashes, login names, session identifiers and authority dumps must not enter audit data.

10. Flush credential and audit persistence before local target-session expiry. Session-revocation failure must roll back database mutation. Preserve the existing documented safe non-atomic behavior if a later commit failure occurs after sessions have already been expired.

11. Every previously authenticated target session must be expired locally. Authentication that verified the old credential before the reset but has not completed final registration must fail through the existing authentication-generation check.

12. The new credential must authenticate after successful reset when the target Account is enabled. The old credential must fail. A disabled target remains unable to authenticate until separately enabled through the existing lifecycle boundary.

13. Concurrent reset/password-change/login scenarios must fail closed. In particular, stale credential comparisons or stale authentication generations must not restore the old credential or create a valid post-reset session.

14. Expose only bounded reset-specific failure reasons. Do not propagate secret-bearing infrastructure causes.

15. Add focused unit coverage and real-MySQL integration coverage for authorization, recent-proof enforcement, self-target rejection, successful reset, disabled-target preservation, lockout clearing, authentication-generation advancement, audit rollback, session-revocation failure, stale/concurrent mutation and in-flight-login invalidation.

16. Preserve all existing authentication, lockout, password-change, lifecycle, assignment, Role/Permission, recent-proof and form-login regressions.

## Non-goals

No anonymous or unauthenticated forgotten-password endpoint.

No email/SMS recovery, reset links, reset tokens or external identity provider.

No local break-glass recovery for loss of all usable administrator credentials.

No implicit Account enablement, role/permission change or administrator elevation.

No forced periodic password changes or new mandatory-change-at-next-login state.

No TOTP enrollment/challenge, MFA recovery/reset, recovery codes or authenticator integration.

No password-work-factor benchmark or supported-hardware qualification.

No production UI/HTTP administration adapter unless current repository implementation requires a minimal composition change to exercise the existing application-service boundary.

No IMP-014 work and no successor TASK allocation.

## Security, privacy and audit

Raw passwords, password hashes and credential-derived values must not enter logs, audit records, exceptions, documentation, test fixtures, CI artifacts or AI context.

Use synthetic generated credentials only.

Authorization and recent-proof checks occur before mutation. Secret validation/hashing must not weaken the existing short-transaction design.

Only stable public UUIDs and fixed non-sensitive action/context values belong in audit evidence.

Existing session fixation, CSRF, concurrency, final-registration generation checks and generic ordinary-login failure behavior must remain intact.

## Migration and deployment

No schema migration is expected. Released V1-V8 remain immutable.

No new runtime dependency, distributed session mechanism, cache, queue or external service is expected.

Deployment remains the existing single application artifact. Rollback is application rollback with the unchanged schema; credentials already successfully reset before rollback remain the new persisted credentials.
