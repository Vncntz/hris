## Relevant baseline and contracts

`DashboardView` is the authenticated root route:

- route path `""`
- layout `MainLayout`
- `@PageTitle("Dashboard")`
- `@Menu(order = 0, icon = "vaadin:dashboard", title = "Dashboard")`
- `@PermitAll`

Its existing welcome/session presentation must remain authenticated and must continue to show only the existing login-name information.

`MainLayout` obtains navigation using:

`MenuConfiguration.getMenuEntries()`

and renders the supplied `MenuEntry` title, path and optional icon. The returned menu entries are already subject to Vaadin route access filtering for the current request/user.

`RouteAuthoritySecurityTest` verifies that the same `MenuConfiguration` result agrees with server-side `NavigationAccessControl` decisions. TASK-0048 must consume that contract rather than implementing its own permission evaluation.

Preserve the relative ordering provided by the access-filtered menu configuration. Do not introduce an independent permission-specific sort or authorization table.

Exclude the Dashboard/self entry from the dashboard's module-navigation options. Prefer route/menu identity such as `MenuEntry.menuClass()` rather than hard-coding a business permission or module name.

## Acceptance criteria

1. `DashboardView` derives module-navigation entries from `MenuConfiguration.getMenuEntries()` or the repository-equivalent current-main menu contract used by `MainLayout`.

2. The Dashboard/self `MenuEntry` is excluded from the module-navigation area.

3. The relative deterministic ordering supplied by the Vaadin menu configuration is preserved for all remaining entries.

4. Every rendered module option uses the corresponding menu title and path and supports the menu's optional icon metadata without inventing module-specific presentation logic.

5. The dashboard renders only entries present in the current access-filtered menu result. It does not inspect authorities directly or recreate server-side route authorization rules.

6. No `client:admin`, role name, permission string, module authorization table or module-specific security condition is hard-coded in `DashboardView`, CSS or dashboard tests.

7. Direct route authorization remains enforced by the existing Vaadin/Spring Security boundary. Dashboard navigation visibility is usability/discoverability behavior only and is never treated as a security boundary.

8. When zero non-dashboard entries are available, the dashboard renders a clear accessible empty state explaining that no additional modules are currently available to the account.

9. When exactly one authorized non-dashboard entry is available, one corresponding module-navigation option is rendered and operates correctly.

10. When multiple authorized entries are available, every supplied authorized entry is rendered once, in menu order, with no Dashboard/self duplication.

11. Tests demonstrate that an entry filtered out by the real access-filtered menu contract is absent from rendered dashboard navigation while an allowed synthetic/test entry is present. Do not depend on the unmerged TASK-0044 Client route to provide this coverage.

12. Module navigation is keyboard operable using normal sequential focus behavior, has meaningful accessible names/semantics, provides clearly visible focus indication and introduces no keyboard trap.

13. Decorative icons are hidden from assistive technology consistently with existing shell conventions. Navigation labels remain programmatically meaningful without relying solely on icons or color.

14. Representative desktop and narrow/mobile browser verification confirms readable module options, usable targets, no clipping/overlap and no horizontal page overflow.

15. Navigation from a rendered module option reaches its intended test/authorized route through normal Vaadin navigation behavior.

16. The existing welcome and session information remain present. The UI must not expose granted-authority values, permission names, security internals, session identifiers or additional authentication information.

17. No fabricated dashboard metrics, counts, workforce data, payroll data or Client Company/Site business data are introduced.

18. Deterministic component/unit coverage includes zero, one and multiple non-dashboard menu entries, Dashboard/self filtering, ordering, title/path/icon handling and empty-state behavior.

19. Rendered/browser verification covers authorized navigation visibility, filtered-entry absence, keyboard/focus behavior, responsive desktop/mobile behavior, horizontal overflow and relevant browser-console errors.

20. Existing application-shell, login and route-security behavior continues to pass without weakened assertions.

21. The complete TASK-0048 diff contains no backend, domain, persistence, Flyway, Spring Security policy or parallel TASK implementation changes.
