## Goal

Polish the existing anonymous HRIS login screen into a responsive, accessible and visually coherent sign-in experience consistent with TASK-0040's authenticated application-shell visual language.

This TASK is frontend/UI only. Authentication behavior, security policy and backend contracts must remain unchanged.

## Scope

Refine the existing `LoginView` at `/login` using current Vaadin/Lumo conventions and the established HRIS branding direction.

The screen must provide:

- clear HRIS branding and sign-in hierarchy;
- an intentionally composed desktop/laptop presentation that remains usable and uncluttered on narrow viewports;
- consistent typography, spacing, surfaces and visual language with the TASK-0040 application shell;
- readable contrast and clearly visible keyboard focus states;
- accessible labels, semantics and logical keyboard navigation;
- a single clear sign-in action with no additional client-side path capable of producing duplicate submissions;
- coherent presentation of the optional authenticator/recovery-code field without changing how its secret value is handled;
- the existing generic authentication-failure behavior without disclosing why authentication failed.

Changes must remain within the login UI, UI-focused tests, and the factual predecessor/task-state documentation required by the combined work-order + implementation PR.

## Acceptance criteria

1. `/login` presents a polished HRIS sign-in experience using the existing HRIS/Lumo visual direction established by TASK-0040, with a clear application identity and sign-in hierarchy rather than an uncomposed default-form presentation.

2. The page remains anonymous and preserves the existing authentication contract exactly: `LoginForm`, POST action `login`, no forgot-password action, existing Spring Security processing and generic `?error` handling.

3. Successful login with a valid synthetic account reaches the existing authenticated HRIS shell. Invalid synthetic credentials produce only the generic failure state and do not reveal whether the username, password, optional factor, account state or another authentication condition caused the failure.

4. The optional authenticator/recovery-code control is clearly identified as conditional/optional for enrolled users and fits naturally into the sign-in flow. Its request-only DOM architecture and all security-sensitive input/submission/clearing properties listed above are preserved.

5. The factor secret is never copied into a server-side Vaadin field, component property, session state, log message, test fixture, screenshot, browser-console message or other persisted/debug representation.

6. Keyboard users can reach and operate all login controls in a logical order without a focus trap. Focus indicators are clearly visible, labels remain programmatically associated with their controls, and failure presentation remains understandable without relying only on color.

7. Desktop, laptop and narrow/mobile-width layouts remain usable without clipped form controls, horizontal overflow, inaccessible content or overlapping branding. The sign-in form remains the visual and interaction priority at every reviewed viewport.

8. Text, inputs, error presentation, buttons and focus indicators have readable contrast. Decorative visuals do not introduce misleading semantics, and motion, if any, respects reduced-motion preferences.

9. The page exposes one clear submission action. Do not add custom authentication handlers, secondary submit buttons or JavaScript submission paths that can bypass or duplicate the existing native login POST behavior.

10. Login failure, optional-factor presentation and any disabled/submitting behavior remain visually understandable and do not leak stack traces, relational/internal identifiers, authentication implementation details, credentials or infrastructure information.

11. Logging out through TASK-0040's existing shell continues to terminate the authenticated session through the existing mechanism and returns the user to the polished login experience.

12. Focused automated tests cover the stable server/UI contract where practical, including login route/access metadata, form action, forgotten-password visibility and generic error behavior. Browser verification covers behavior that depends on the rendered DOM, including the optional factor.

13. No unrelated authenticated shell redesign, Client Company/Site UI or successor functionality is introduced.
