## Goal

Establish the smallest maintainable Spring Boot configuration foundation that explicitly separates:

- repository-safe defaults;
- development/test configuration;
- installation-specific external configuration;
- protected externally supplied secrets.

The convention must work for supported Windows and Ubuntu deployments without implementing later installer, Agency configuration, authentication, or deployment capabilities.

## Current repository baseline

At planning time:

- `hris-app/src/main/resources/application.properties` contains only the application name and Flyway configuration;
- `application-dev.properties` binds the development server to `127.0.0.1`;
- `.gitignore` excludes `.env` and `.env.*` while allowing `.env.example`;
- no committed production datasource credentials or other application secrets exist;
- MySQL integration tests use disposable test configuration;
- `docs/deployment/README.md` does not yet define production configuration procedures.

Preserve this safe baseline unless implementation evidence justifies a narrow change.

## Non-goals

- No HRIS-managed MySQL installation.

- No Agency/business configuration root.

- No audit persistence.
- No cloud/Vault/Kubernetes secrets infrastructure.

## Implementation direction

1. Verify Spring Boot 4.1.1 externalized-configuration behavior from current official Spring Boot documentation before choosing exact external file, configuration-import, environment-variable, or configuration-tree behavior.

2. Prefer built-in Spring Boot configuration mechanisms. Do not create a custom configuration loader without a demonstrated requirement.

3. Keep committed `application.properties` and profile resources safe for a public repository. No production credentials or installation-specific secret values may be committed.

4. Define the configuration model clearly:
   - committed safe defaults;
   - explicitly activated development/test profiles;
   - external installation configuration;
   - protected secret-bearing values supplied outside source control.

5. Respect D-029's logical deployment layout. Windows machine-wide configuration/secrets belong under the `%ProgramData%\HRIS` area; Ubuntu configuration/protected secrets belong under `/etc/hris`. The later installer may determine exact subdirectory/service wiring.

6. Do not infer production configuration paths from the developer working directory, home directory, username, drive letter, host locale, or other machine-specific developer state.

7. Do not make `.env` parsing a production requirement unless the work order is explicitly revised to authorize and justify it.

8. Add focused automated verification proving the selected standard Spring Boot mechanism can load external synthetic configuration and override a safe value.

9. Prove that development configuration remains explicitly activated and is not silently enabled for the default runtime.

10. Where the task introduces required technical configuration, invalid or missing values must fail clearly rather than silently falling back to an unsafe value.

11. Document that secret values must not be committed or emitted in normal logs/diagnostic output. Future diagnostics must redact them in accordance with D-024.

12. Use unmistakably synthetic placeholders/examples only.

## Acceptance criteria

1. A documented configuration convention distinguishes repository defaults, profiles, installation configuration, and protected secrets.

2. Committed runtime resources contain no production credential, secret, private key, reusable password, or customer-specific value.

3. An automated test proves a supported external configuration source can override a safe synthetic property without relying on a pre-existing machine installation.

4. Configuration tests are portable and do not depend on a developer username, home directory, Windows drive letter, or host-specific HRIS directory.

5. Development profile behavior remains explicit rather than becoming a production/default profile.

6. `.env` is not silently promoted to a required runtime mechanism.

7. Windows and Ubuntu logical configuration/secret locations are documented consistently with D-029 while installer/file-ACL automation remains later scope.

8. Secret examples are synthetic and secret values are explicitly excluded from source control, normal logs, and diagnostics.

9. No Agency configuration, authentication/RBAC, audit persistence, installer, MySQL provisioning, TLS provisioning, backup/recovery, or later IMP behavior appears in the diff.

10. No unnecessary production dependency is introduced.

11. Focused configuration tests and the ordinary Maven reactor pass.

12. Existing application smoke and Linux MySQL/Flyway regression paths remain green in normal CI.

13. Exact-head `ci / policy`, `ci / build-linux`, and `ci / build-windows` pass on the final combined-PR head.
