# TASK-0011 — Append-only audit persistence foundation

Status: POST_MERGE_VERIFIED / complete

Parent implementation item: [IMP-008](../implementation/tasks/IMP-008.md)

## Goal

Implement the minimum reusable append-only audit facility that later HRIS modules can call from their transactional application-service boundaries.

Provide a JDK-only neutral audit contract in `shared-kernel`, a JPA/Hibernate implementation owned by `platform-operations`, and a real-MySQL schema whose audit records cannot be updated or deleted through normal database statements.

## Implementation direction

1. Add the smallest neutral audit contract to `shared-kernel`.

   It must describe an audit request with:
   - explicit actor reference;
   - action;
   - target type;
   - target reference;
   - optional reason;
   - optional privacy-minimized context.

   The contract must use existing neutral primitives where appropriate and must not depend on Spring/JPA/security/business modules.

2. Provide an append-oriented interface such as an `AuditRecorder` contract. Normal callers must not receive update/delete capabilities.

3. The `platform-operations` implementation owns:
   - event public-ID generation using the existing UUID/PublicId convention;
   - UTC event timestamping through an injected `java.time.Clock`;
   - validation/bounded text behavior;
   - transaction-aware persistence.

   Do not use the host default time zone or locale.

4. Use JPA/Hibernate as the normal persistence mechanism.

   Add only the dependencies actually required by `platform-operations`, including `shared-kernel` and the repository's Boot-managed JPA support. Do not pin versions already governed by the existing BOM.

5. Keep the JPA persistence model internal to `platform-operations`.

   Prefer an explicit persistence component using `EntityManager.persist` or another append-only JPA surface rather than publishing a generic CRUD repository that advertises mutation/deletion operations.

   Do not expose JPA entities as public cross-module contracts.

6. Allocate global Flyway migration:

   `V2__create_audit_event.sql`

   Refresh `main` immediately before implementation and confirm V2 remains the next free version.

7. V2 must create the audit-event storage needed for D-065, including:

   - compact internal relational primary key where appropriate;
   - unique stable UUID/public identifier in a compact database representation;
   - UTC-capable occurrence timestamp;
   - actor reference;
   - action;
   - target type/reference;
   - optional reason;
   - optional context.

   Choose bounded column sizes deliberately and document them.

8. Protect append-only integrity at the database level.

   Add MySQL-compatible safeguards that reject UPDATE and DELETE operations against the audit-event table. Keep INSERT and read/query behavior available.

   Verify the exact MySQL syntax against official documentation during implementation if needed; do not infer unsupported behavior.

9. Ensure UTC persistence is unambiguous.

   Verify the JPA/Hibernate/MySQL mapping actually round-trips a fixed `Instant` correctly against real MySQL and does not depend on the host default time zone. Use explicit Hibernate/JDBC configuration if required by the verified mapping.

10. Transaction behavior must be predictable.

   Audit recording must join an existing application transaction where present. Add a real-MySQL test proving that an audit insert rolls back when the surrounding transaction rolls back.

11. Add real-MySQL verification proving at least:

   - clean Flyway migration through V2;
   - audit append succeeds;
   - generated public event ID is persisted uniquely;
   - fixed UTC timestamp round-trips correctly;
   - actor/action/target/reason/context round-trip;
   - attempted UPDATE is rejected;
   - attempted DELETE is rejected;
   - surrounding transaction rollback leaves no audit row.

12. Update the existing Flyway/MySQL regression assumptions for the new released migration.

   `MySqlDatasourceIT` currently assumes exactly one migration. Update it for the V2 history without weakening:
   - V1 immutability/checksum verification;
   - repeat `validate()` behavior;
   - zero new migrations on a second `migrate()`;
   - duplicate/conflicting V1 failure behavior.

13. Add focused unit tests for validation/contract behavior that run in ordinary Windows and Linux reactor builds without MySQL.

14. Document the audit facility under `docs/modules/`, including:
   - ownership;
   - append-only guarantee;
   - caller responsibilities;
   - transaction behavior;
   - actor remains caller-supplied until Identity & Access integration;
   - context privacy rules;
   - audit complements rather than replaces domain history.

## Acceptance criteria

1. `shared-kernel` contains only neutral audit contracts and remains free of Spring/JPA/infrastructure dependencies.

2. `platform-operations` owns the concrete audit persistence implementation.

3. Normal application audit API provides append behavior but no update/delete contract.

4. JPA/Hibernate is used for normal audit persistence.

5. A released-forward Flyway V2 creates the audit schema; V1 is untouched.

6. Audit rows contain stable event ID, UTC time, actor, action, target, optional reason, and optional context.

7. Event timestamp generation uses an injectable clock and does not rely on host timezone/locale.

8. Real MySQL proves an appended audit event round-trips accurately.

9. Real MySQL rejects direct UPDATE and DELETE attempts against audit records.

10. A rolled-back surrounding transaction does not leave an audit event behind.

11. Existing Flyway history/checksum/conflict regression coverage remains meaningful after V2.

12. Audit context/examples use synthetic values only and documentation prohibits secrets and unrestricted personal/payroll payloads.

13. No authentication, RBAC, domain call sites, UI, Envers, outbox, or later-IMP work appears in the diff.

14. Focused tests, ordinary `clean verify`, and real-MySQL `-Pmysql-it clean verify` pass locally.

15. `python tools/plan-index.py --check`, changed Markdown links, frozen-planning changed-path verification, `git diff --check`, dependency review, and complete diff review pass.

## Security, privacy, audit, migration, and deployment

The audit facility itself is security-sensitive durable data.

Do not place raw credentials, private keys, secret configuration, uploaded documents, government identifiers, payroll line details, or arbitrary entity dumps into audit context.

Audit persistence does not replace authoritative domain history.

V2 is a forward migration creating new technical/platform storage only. No production data transformation or destructive operation is authorized.

No deployment/installer change is required.
