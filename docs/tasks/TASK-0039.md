## Goal

Add a bounded, authorization-protected Client Management administration query contract for browsing Client Companies and their Client Sites.

The contract must give later Vaadin administration UI enough information to list and select Client Company/Site records without exposing Client Management JPA entities, repositories, relational identifiers, persistence state, or unbounded table reads.

## Scope and acceptance criteria

1. Client Management owns a public administration/query contract that can enumerate Client Companies in bounded pages.

2. The contract can enumerate Client Sites belonging to one specified Client Company in bounded pages.

3. Every page request has a finite enforced upper bound. Invalid offsets, limits, targets, or other query arguments fail deterministically. Do not add an unbounded `findAll`-style public contract.

4. Results use immutable projections only. Company administration rows may expose only:
   - stable public UUID;
   - display name;
   - active state;
   - edit version.

5. Site administration rows may expose only:
   - stable public UUID;
   - parent Company public UUID;
   - display name;
   - stored Site active state;
   - parent Company active state or equivalent effective-activity information;
   - edit version.

6. The query API must provide enough bounded paging information for a later lazy UI consumer to determine whether additional rows exist or otherwise obtain a bounded/appropriate result count. Do not expose repository/page implementation types as the module's public API.

7. Results have stable deterministic ordering suitable for repeatable pagination. The ordering must include a stable tie-breaker so equal display names cannot produce ambiguous page membership.

8. Company/Site descriptive names are not required to be unique. Duplicate names must remain distinguishable by stable public UUID and must not cause pagination loss or duplication.

9. Administration browse operations require the existing `client:admin` authority through the authenticated `CurrentActor` boundary. Caller-supplied user/actor identifiers must not influence authorization.

10. Read transactions are short, read-only, READ COMMITTED and independent of ambient caller transactions. Administration queries must observe current committed Client lifecycle/version state rather than inherit an older caller snapshot.

11. The administration query contract must not expose:
    - JPA entities;
    - Spring Data repositories;
    - relational/database IDs;
    - lazy persistence state;
    - SQL or infrastructure causes;
    - credentials, session identifiers, or request payloads.

12. Preserve the existing `ClientReferences` known-UUID contract and TASK-0036/TASK-0037 mutation, authorization, locking/version, audit and lifecycle semantics unless a minimal compatible internal refactor is strictly required.

13. Add deterministic unit coverage for authorization, bounded paging validation, transaction definition, projection boundaries and deterministic ordering behavior.

14. Add real-MySQL integration coverage proving:
    - multiple Companies page deterministically;
    - duplicate Company display names remain distinct;
    - Sites are restricted to their requested parent Company;
    - duplicate Site display names remain distinct;
    - inactive/effective lifecycle state is represented correctly;
    - page boundaries do not duplicate or omit records;
    - administration reads observe a separately committed lifecycle/version change despite an older ambient caller snapshot.

15. Architecture verification must continue proving that Client Management entities/repositories remain private implementation details and that consumers interact through module-owned contracts.

## Security, privacy, and audit

Administration browse access is authenticated and least-privilege protected by the existing Client administrator authority.

These operations are reads and do not create mutation audit events.

Return only data required for Client master administration. Do not add personal/contact data, credentials, security/session data, arbitrary persistence metadata or infrastructure details.

Tests and fixtures must use synthetic data only.
