# TASK-0022 — Persist authorization roles/permissions and load runtime authorities

Status: PLANNED — implementation awaits verified planning integration and a separate explicit work cycle.

Parent implementation item: [IMP-013](../implementation/tasks/IMP-013.md)

## Goal and scope

Establish the first IMP-013 authorization slice: durable Role/Permission/account-assignment persistence owned by Identity & Access and real authenticated authorities derived from those assignments.

Today `AccountAuthenticationProvider` authenticates a valid account with an empty authority collection even though `CurrentActor` already exposes `hasAuthority(...)` and `requireAuthority(...)`. This TASK closes that foundation gap without implementing the administrative account-management workflow.

Affected implementation is primarily:

- `modules/identity-access`;
- the next global Flyway migration under `hris-app/src/main/resources/db/migration`;
- focused identity-access unit tests;
- focused real-MySQL integration verification under `hris-app`;
- minimal mutable implementation/task documentation.

No Vaadin administration screen is required.

## Acceptance criteria

1. Identity & Access owns durable Role and Permission persistence plus Account-to-Role and Role-to-Permission membership. Internal JPA entities/repositories remain module-internal and are not exposed to other modules.

2. If V5 remains the next free global Flyway version, add a forward migration for authorization persistence. Released V1–V4 remain byte-for-byte unchanged. The schema enforces unique role public IDs, deterministic/canonical role identity or naming, unique permission authority keys, unique account-role memberships, unique role-permission memberships, valid foreign keys, and deliberate indexes for authentication-time authority lookup.

3. No default account, administrator credential, administrator assignment, customer value, reusable secret, or vendor-known password is seeded. Synthetic tests may create ephemeral accounts/roles/permissions only within isolated test data.

4. Successful authentication obtains authorities from the authenticated account's persisted, enabled assignments. Authorities are deterministic and deduplicated. An account with no assigned permission continues to authenticate with zero authorities. Disabled/inapplicable roles must not grant authority.

5. The existing `SecurityCurrentActor.hasAuthority(...)` and `requireAuthority(...)` behavior works with authorities produced by a normal `AccountAuthenticationProvider` authentication. Existing authentication, canonical-login, password-hash, lockout, disabled-account, and generic bad-credentials behavior remains intact.

6. Authority membership is a login/session snapshot for this TASK. Changes made directly by tests or future administration become effective for a new authentication; live distributed session invalidation or a generalized authorization cache is out of scope. Document this boundary so later administrative work can add explicit revocation/re-authentication behavior where required.

7. Focused unit tests cover authority derivation, deduplication, no-role/no-permission behavior, disabled role behavior, and `CurrentActor` success/failure behavior. Real-MySQL tests prove the migration, relational constraints, account-role/role-permission joins, and authentication-time authority propagation.

8. Existing architecture tests, Windows reactor verification, Linux MySQL verification, task-context/tooling tests, and policy checks remain green. No test may weaken or delete valid prior assertions merely to obtain green CI.

9. Mutable documentation records TASK-0020/TASK-0021 closeout, IMP-012 closure, IMP-013 activation, and TASK-0022's verified implementation evidence. Frozen planning files remain unchanged.

## Security and privacy

Do not log credentials, hashes, entered passwords, MFA material, or authorization-sensitive secret material.

Role and permission identifiers may be stored in the authenticated security context because they are non-secret authorization metadata; credentials remain absent.

Avoid broad authorization failure detail that would disclose account state unnecessarily.

Do not use customer data.
