# IMP-004 — MySQL/Testcontainers development and test environment

## Milestone and status

M0 — Engineering Foundation. P0. READY FOR IMPLEMENTATION; implementation has not started.

Focused work order: [TASK-0007](../../tasks/TASK-0007.md).

## Objective

Establish a simple, reproducible real-MySQL development and test foundation that later persistence, migration, payroll, attendance, and repository work can rely on.

The baseline targets MySQL 8.4 LTS-line behavior, ephemeral Testcontainers-or-equivalent MySQL for automated integration tests, ordinary Maven Wrapper commands, CI-compatible execution, explicit Windows/Linux portability, and no H2 substitution for MySQL semantics.

## Authority and dependencies

Frozen Master Plan §65.1 and decisions D-023, D-108, D-109, D-119, D-130, D-132, D-135, D-143, D-144, D-149, and D-177; [execution rules](../EXECUTION_RULES.md); [implementation state](../IMPLEMENTATION_STATE.md); [repository workflow](../REPOSITORY_WORKFLOW.md).

The frozen backlog names IMP-001 as the formal predecessor. Repository reality also provides completed IMP-003 CI, completed IMP-087 maintenance, and the current trusted-main integration tooling. No approved ADR applies.

## Scope

IMP-004 may include, through focused TASK work orders:

- Maven dependencies and configuration needed for real-MySQL integration testing;
- the MySQL JDBC driver;
- Testcontainers MySQL support or an equivalent ephemeral-container mechanism;
- Spring Boot datasource/test configuration;
- a reusable test-container bootstrap pattern;
- a minimal real-MySQL integration test proving connectivity and Spring wiring without business schema;
- local development MySQL support only where a concrete workflow justifies it;
- CI changes necessary to run selected real-MySQL integration tests reliably;
- developer/test documentation for the resulting workflow.

[TASK-0007](../../tasks/TASK-0007.md) is deliberately narrower: establish the automated real-MySQL integration-test baseline first. Persistent local database provisioning and Docker Compose are not required by that first work order.

## CI direction

Keep the current stable ci / policy, ci / build-linux, and ci / build-windows structure unless implementation evidence requires otherwise.

Run the selected container-backed MySQL integration test once on the Ubuntu job through an ordinary Maven activation, while retaining the current Windows reactor verification without duplicating the OS-neutral database test. The same Maven activation must remain runnable outside GitHub Actions on a developer machine with a compatible container runtime.

This follows D-144/D-149: real MySQL remains part of PR qualification while expensive OS-neutral database behavior is not needlessly executed twice. GitHub documents container/service-container support on GitHub-hosted runners as Linux/Ubuntu-only; exact Testcontainers behavior and implementation mechanics must still be verified during TASK-0007.

## Explicit non-goals

Do not pull these items into IMP-004:

- Flyway migration conventions or production migrations — IMP-005;
- common UUID/money/time primitives — IMP-006;
- configuration/secrets framework beyond the minimum test/runtime wiring needed here — IMP-007;
- audit implementation — IMP-008;
- authentication/RBAC — IMP-009;
- synthetic-data generator implementation — IMP-010;
- executable module-boundary architecture tests — IMP-011;
- business entities, aggregates, repositories, or tables created merely to prove database access;
- payroll, attendance, recruitment, billing, compliance, or other business behavior;
- production MySQL installer/service packaging;
- production backup/recovery;
- performance tuning or benchmark claims;
- customer-specific database configuration;
- H2 as proof of MySQL compatibility.

## Acceptance direction

IMP-004 is complete only when applicable work orders prove that:

1. the project can start the selected database integration context and test against a real supported MySQL 8.4 LTS-line instance;
2. automated integration tests can provision an isolated MySQL instance without manual database setup;
3. the database is disposable/test-only and uses synthetic/non-customer data;
4. tests use ordinary Maven Wrapper commands;
5. MySQL-specific behavior is not silently validated against H2;
6. the baseline requires no business schema implementation;
7. Windows/Linux CI implications are deliberate and documented;
8. IMP-005 can add Flyway on top of the baseline without redesigning the test environment.

Exact dependency versions, container image tags, and Spring Boot/Testcontainers integration conventions are implementation-time verification items, not guessed planning values.

## Security, privacy, audit, migration, and deployment

Use only disposable development/test credentials and synthetic data. Do not commit secrets or customer production data. No application audit behavior is introduced by the baseline.

IMP-004 must not create or alter production schema migrations. Production MySQL installation, service management, backup/recovery, and customer deployment configuration remain outside this item.
