## Objective and authority

Make the modular-monolith architecture rules executable in normal Maven verification so accidental boundary erosion fails CI rather than relying only on documentation and code review.

Relevant frozen authority includes Master Plan §§46, 47, and 65.1 and Decisions D-109, D-110, D-132, D-147, D-148, D-149, and D-177.

Key requirements include:

- no cyclic business-module dependencies;
- no direct cross-module repository/persistence access;
- JPA entities must not become cross-module API contracts;
- cross-module interactions must use intentional application/query contracts;
- `shared-kernel` must remain small and neutral;
- prohibited infrastructure such as Kafka or Redis must not be casually introduced without an approved architecture decision;
- architecture rules must execute in normal CI.

No approved ADR applies.

Do not modify frozen planning sources.

## Current repository state

At IMP creation:

- the root Maven reactor contains the parent plus 16 child modules/projects;
- no ArchUnit or equivalent architecture test currently exists;
- `hris-app` is the composition root and already depends on all production application modules;
- normal `hris-app` tests already use the repository-managed JUnit/Spring Boot test stack;
- Linux CI runs `./mvnw -B -Pmysql-it clean verify`;
- Windows CI runs `.\mvnw.cmd -B clean verify`;
- both commands therefore provide an existing execution path for architecture tests without a CI workflow redesign;
- current JPA entities in Identity & Access and Platform Operations are package-private;
- the current Spring Data repository in Identity & Access is package-private;
- `shared-kernel` currently contains only neutral JDK-oriented primitives/contracts;
- most future business modules remain structural placeholders, so a final M1+ inter-module dependency matrix would be premature;
- the root already uses Maven Enforcer and can carry narrowly scoped dependency-policy enforcement without adding another build framework.

## Scope and acceptance direction

IMP-011 establishes the smallest executable architecture guardrail set justified by the current codebase.

The focused implementation should:

- use ArchUnit core from ordinary JUnit tests;
- host architecture tests in the existing `hris-app` test source set, because that composition-root module already has visibility to the application modules;
- keep ArchUnit strictly test-scoped;
- import production classes while excluding test classes;
- enforce that module/package slices are free of dependency cycles;
- enforce that JPA entity classes remain module-internal rather than public cross-module contracts;
- enforce that Spring Data repository types remain module-internal;
- enforce that `shared-kernel` does not depend on business modules or the application/composition root;
- enforce that business/module code does not depend on the `hris-app` composition/UI layer;
- enforce that Vaadin remains an application/UI concern rather than leaking into business modules;
- establish an executable guard against currently prohibited Kafka/Redis infrastructure dependencies, preferably by extending the existing Maven Enforcer policy so an unused dependency cannot evade a class-level rule;
- produce clear failure messages that tell a future developer which architectural boundary was violated;
- document which rules are mechanical now and which still require task/ADR review because the corresponding future package/contracts do not yet exist.

Use a pinned ArchUnit version. At planning time `1.5.1` is the verified upstream release.

Do not create a separate architecture-testing Maven module unless implementation evidence proves `hris-app` cannot reliably host the rules.

## Boundaries

Do not:

- implement IMP-012 or another M1 business capability;
- invent a complete future inter-module dependency allowlist before those application/query contracts exist;
- reorganize every module into speculative `domain/application/infrastructure/api` package layers solely to make the test suite look complete;
- introduce JPMS;
- introduce Spring Modulith or another application framework for this task;
- add Kafka, Redis, a broker, distributed infrastructure, or a service mesh;
- add runtime dependencies to business modules merely for architecture testing;
- change production authentication, audit, persistence, synthetic-data, payroll, compliance, or UI behavior;
- add or modify Flyway migrations;
- change protected-main settings or required-check configuration;
- modify frozen planning sources.

Where a frozen architectural rule cannot yet be mechanically proven without inventing future structure, retain it as a documented review obligation rather than adding speculative scaffolding.

## Dependency and test direction

Prefer:

- root property/dependency management for the pinned ArchUnit core version;
- one test-scoped `com.tngtech.archunit:archunit` dependency in `hris-app`;
- ordinary JUnit tests using `ClassFileImporter`;
- `ImportOption.Predefined.DO_NOT_INCLUDE_TESTS` or equivalent;
- the existing Maven Enforcer plugin for dependency-family bans where class-level inspection is insufficient.

Architecture tests must run as part of ordinary `test` / `verify`; no separate CI job is required.

The implementation should not materially increase operational/runtime complexity because all new architecture-test dependencies remain build/test only.

## Completion direction

TASK-0014 may close IMP-011 if it establishes executable, CI-running architecture rules that protect the currently enforceable modular-monolith boundaries, documents the intentional limits of those rules, and introduces no unrelated domain or infrastructure work.

Completion of IMP-011 means the M0 architecture-test foundation exists. It does not mean every future M1–M6 module interaction has already been designed or encoded.
