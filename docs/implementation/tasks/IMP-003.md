# IMP-003 — CI baseline

## Milestone and status

M0 — Engineering Foundation. P0. COMPLETE (2026-09-29) on the task branch; PR #3 targets `main` and awaits integration.

Focused work order: [TASK-0002](../../tasks/TASK-0002.md).

## Objective

Run the existing Maven reactor and tests in GitHub Actions on Ubuntu and Windows, with stable job names that can support protected `main` after a future governance decision. The user directed on 2026-09-29 that the current protection rule remain unchanged.

## Authority and dependencies

Frozen Master Plan §65.1 and decisions D-131, D-132, D-134, D-143, D-144, D-147, and D-149; [execution rules](../EXECUTION_RULES.md); [implementation state](../IMPLEMENTATION_STATE.md); [repository workflow](../REPOSITORY_WORKFLOW.md). IMP-001 supplies the Maven reactor. IMP-002 supplies repository governance. No approved ADR applies.

## Scope

- Add a read-only GitHub Actions workflow for pull requests, task-branch pushes, and post-merge pushes to `main`, using JDK 25 and the checked-in Maven Wrapper. Newer runs for the same PR cancel older in-progress PR runs without intentionally cancelling `main` push validation.
- Verify compile, packaging, and current unit/smoke tests with `clean verify` on Ubuntu and Windows. Use stable, unique job names suitable for branch protection.
- Document the equivalent local commands and the current coverage boundary.
- Run the workflow remotely and inspect the actual check names and results. Leave `main` protection unchanged under the latest explicit user instruction.

Architecture tests belong to IMP-011 and the MySQL/Testcontainers test environment belongs to IMP-004. This task may wire in those suites only if they already exist; it must not create fake passing checks or implement their test infrastructure. Flyway, payroll regression tests, and performance tests likewise have no implementation yet.

## Acceptance criteria

1. The workflow runs the full Maven reactor with required tests on both OS families using ordinary repository commands for PRs, task branches, and `main` pushes. The job names remain stable across events; concurrency isolates PRs and preserves each `main` push run.
2. CI has least-privilege repository access, no customer data or secrets, and no deploy or artifact publishing step.
3. Local `clean verify` and workflow syntax/structure checks pass. Remote runs prove the expected named jobs pass before any status check is made required.
4. The remote protection rule remains unchanged under the explicit user instruction; read it back independently and record that the checks are not required.
5. Documentation and mutable implementation state accurately distinguish completed verification from deferred suites or remote controls.

## Required verification

- `./mvnw -B clean verify` on Ubuntu CI and `.\mvnw.cmd -B clean verify` on Windows CI; locally run the available OS command.
- Inspect the GitHub Actions run and exact job contexts, including failed/skipped tests.
- Check workflow YAML and complete diff, `git diff --check`, task links, frozen-file and scope boundaries.
- Read back branch protection and verify that no setting changed. Do not make a nonexistent or unverified context required.
- After PR #3 is merged, verify the first `main` push run passes both named jobs before beginning IMP-004.

## Security, audit, migration, and deployment

The workflow needs only `contents: read`. Do not expose secrets, real customer data, or build artifacts. It changes no application authorization, audit behavior, database schema, runtime configuration, or deployment process. Required status checks are a remote governance setting, recorded separately from source changes.
