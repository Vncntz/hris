## Relevant Frozen Architecture and Governance

- The repository remains one Maven multi-module modular monolith and one deployable application (D-109/D-138). Governance files must not alter module ownership, build dependencies, or runtime topology.
- Root `AGENTS.md` is a short global contract with a reading order and links to canonical documents; module `AGENTS.md` files are selective, not boilerplate (D-139).
- Small indexed Markdown files under `docs/` are the durable engineering record. ADRs use stable `ADR-####` IDs; accepted history is preserved through superseding ADRs (D-140).
- A private GitHub repository, protected `main`, short-lived branches/worktrees, and reviewable pull requests are the collaboration baseline. Build/test commands remain usable outside GitHub (D-131).
- Agents may prepare branches and PRs within granted permissions but may not bypass protected-main controls or merge `main` without explicit human approval (D-134 and the execution rules).
- Normal development, CI, AI context, and synthetic datasets may not contain real customer production data (D-132).

## Task-Path Convention

The frozen Master Plan §65.8 says each selected `IMP-###` backlog item becomes one or more checked-in `TASK-####.md` specifications. D-135 places meaningful work normally at `docs/tasks/TASK-####.md`. The current mutable implementation state and completed IMP-001 precedent use `docs/implementation/tasks/IMP-###.md` for implementation-item control. These are two levels of record, not interchangeable paths:

- `docs/implementation/tasks/IMP-###.md` holds the implementation backlog item's scope, status, and completion evidence; this file is the IMP-002 control specification required by the current workflow.
- `docs/tasks/TASK-####.md` holds a focused execution work order linked to its parent IMP item. It contains D-135's minimum fields: goal, non-goals, affected modules, relevant decisions/ADRs, acceptance criteria, tests, documentation, and migration/deployment implications.
- During IMP-002 execution, create the first available `TASK-####.md` for this governance work before making governance changes. Link it to IMP-002 and avoid duplicating or diverging requirements. Subsequent IMP items use the same mapping. Keep existing IMP files in place; do not rename or move historical records.
- Index both paths from `docs/README.md` and explain ID allocation/cross-linking in `docs/tasks/README.md`. Do not claim `docs/implementation/tasks/` replaces the frozen `docs/tasks/` convention.

This resolution follows Master Plan §65.8 and D-135, with the current implementation state/IMP-001 file supplying the separate IMP control-file convention. The frozen plan does not specify the first numeric TASK ID or a full task-template layout; choose the first unused four-digit ID after inspecting the repository and record it in the index.

IMP-001 has an IMP control file but no corresponding `docs/tasks/TASK-####.md` in the current repository. Record this as historical convention drift; do not expand IMP-002 into retroactive IMP-001 documentation cleanup.

## In Scope

1. Add a concise root `AGENTS.md` with the mandatory reading order, one-task rule, module/write boundaries, prohibited architecture shortcuts, testing and Definition of Done expectations, privacy/secrets rules, migration/compliance cautions, and links to authoritative planning, execution, state, task, and docs indexes. State the source precedence accurately; do not copy the entire plan.
2. Establish the D-140 documentation taxonomy with `docs/README.md` as the discoverable index. Provide navigable entry points for architecture/ADRs, domain, modules, compliance, deployment, migrations, releases, support, OS, performance, bugs, features, tasks, and known issues. Minimal index/README files may anchor otherwise empty directories; do not invent domain content or legal facts.
3. Define task ID, IMP-to-TASK linking, minimum task fields, status, and retention conventions. Create the focused TASK work order for IMP-002 as specified above. Define an ADR index and minimal ADR record/supersession convention, without fabricating an architecture decision or creating an accepted ADR.
4. Add a thin Cursor rule/pointer only if the repository's intended Cursor configuration is confirmed during implementation. It must link to `AGENTS.md` and canonical docs, not restate or override policy. Record a verified reason if no Cursor rule is installed.
5. Document branch naming, one-task/one-focused-PR scope, PR description and verification evidence, review/merge authority, and treatment of checks that do not yet exist. Add a PR template that prompts for linked IMP/TASK IDs, scope, verification, security/privacy/audit, migration/deployment effects, documentation, and remaining issues, with “not applicable” allowed where justified.
6. Configure and verify remote protection for `main` if authorized access exists. Normal changes must require a PR; agent credentials must not bypass protection or merge without explicit human approval; force-push and deletion must be disallowed. Record the actual rule/settings and evidence in the IMP-002 completion record. If access, plan, or a review path prevents enforcing a required control, leave IMP-002 incomplete and report the blocker. Do not weaken the human checkpoint to make solo work mergeable.
7. Update mutable task/state documentation only after the governance artifacts and remote controls have been verified.

## Out of Scope

These belong to IMP-003 through IMP-011 or later work.

Do not create module-level `AGENTS.md` files without a concrete module invariant and task need; do not create placeholder ADRs, business/domain rules, compliance rates, customer data, bug/feature records, release runbooks, or customer-specific forks. Do not reorganize or rename completed IMP-001 artifacts. Do not configure nonexistent required CI status checks as though IMP-003 has run; document the handoff for enforcing them when checks exist.

## Architectural, Security, and Operational Implications

Affected business modules: none; this is repository-wide governance. No database migration, production deployment, data conversion, or runtime behavior is involved. The security effect is repository access control and the privacy instructions in `AGENTS.md`/PR conventions. The audit evidence for this task is the recorded branch-rule state, linked task/PR conventions, and reviewed Git diff; it is not the application audit foundation (IMP-008).

Remote protection must be checked against the actual private GitHub repository and current permissions. A local Markdown claim alone cannot satisfy the branch-protection criterion. Do not put credentials or private data into the evidence record.
