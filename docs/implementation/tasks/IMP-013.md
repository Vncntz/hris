## Boundaries

- Do not couple User identity to Worker identity.
- Do not implement SSO, Active Directory, LDAP, OAuth/OIDC login, cloud identity providers, email/SMS recovery, a generalized policy engine, customer-specific authorization forks, Redis/distributed sessions, or a complete future-module permission catalog unless a later authorized decision changes scope.
- Do not move security-principal ownership into Platform Operations or another business module.
- Do not expose another module's JPA entity or repository.
- Do not add an administrator account, password, MFA secret, recovery code, or reusable credential to source, migrations, tests, logs, documentation, CI artifacts, or AI context.
- Business-module authorization call sites belong to the task that implements or hardens the applicable operation unless explicitly included in a focused IMP-013 work order.

## Database direction

Released migrations are immutable. Later schema evolution must use forward Flyway migrations and preserve normalized relational integrity for Identity & Access ownership. Do not seed default accounts, administrator assignments, credentials, or customer values.

## Security, privacy, and audit

Authorization is enforced at application-service boundaries rather than relying only on UI visibility. Only stable non-secret identity/authority data may be retained in authenticated session state. Raw passwords, hashes, MFA/recovery material, and login secrets must not enter audit context, ordinary logs, diagnostics, committed fixtures, or task documentation. Administrative mutations must use the existing append-only audit boundary when applicable.

## Verification direction

Each child TASK defines focused tests and relevant regressions. Persistence/MySQL behavior uses the existing Linux `mysql-it` profile when applicable; Windows retains the ordinary reactor build. Architecture rules and Identity & Access ownership must stay green. No test may depend on real customer data or reusable production credentials.
