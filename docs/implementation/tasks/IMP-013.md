## Objective and authority

Implement the Identity & Access capabilities required to administer users and enforce real application permissions while preserving the existing offline-capable authentication foundation.

Identity & Access exclusively owns User/security-principal state, Role, Permission, authentication state, and authorization assignments. User identity remains separate from Worker identity.

Relevant frozen authority includes Master Plan §29 and §65.1 plus D-064, D-065, D-089, D-106, D-109, D-110, D-111, D-112, D-132, D-143, D-148, D-151, and D-177.

No approved ADR changes this direction.

Do not modify frozen planning sources.

## Current implementation baseline

`modules/identity-access` currently owns `AccountEntity`, authentication, password hashing, lockout state, `AccountPrincipal`, and `CurrentActor`.

`AccountAuthenticationProvider` currently authenticates a valid account with an empty authority collection. Consequently, the existing `SecurityCurrentActor.hasAuthority(...)` and `requireAuthority(...)` boundary is structurally present but no persisted role/permission assignment can currently make an authority true in a normal production authentication.

The released global Flyway stream ends at V4. V3 created `identity_account`; V4 created the Agency configuration root.

No Role, Permission, account-role, or role-permission persistence exists on current `main`.

## Scope and completion direction

Implement IMP-013 through focused TASK work orders.

The initiative must eventually provide:

- durable Role ownership inside Identity & Access;
- durable Permission definitions/keys and Role-to-Permission assignments;
- User/Account-to-Role assignments;
- authenticated authorities derived from the account's current persisted assignments;
- administrative account creation and enable/disable lifecycle;
- secure credential creation/change flows appropriate to the supported local deployment model;
- least-privilege administrative application-service boundaries;
- audited changes to accounts, roles, permissions, and assignments;
- a controlled first-administrator/bootstrap path that never relies on a repository-known, vendor-known, or hardcoded production credential;
- appropriate privileged-account offline MFA support consistent with D-151;
- explicit integration of authenticated `CurrentActor` authorization into administrative operations and, when owned by later work, business-module application-service boundaries.

Use stable public IDs where records cross application boundaries. Keep internal JPA entities and repositories private to Identity & Access.

TASK-0022 establishes the first persistence/runtime-authorization slice. Do not infer IMP-013 completion from TASK-0022 alone. Select any later TASK only after TASK-0022 is post-merge verified and the remaining IMP scope is reviewed.

## Boundaries

Do not couple User identity to Worker identity.

Do not implement SSO, Active Directory, LDAP, OAuth/OIDC login, cloud identity providers, email/SMS password recovery, a generalized policy engine, customer-specific authorization source forks, Redis/distributed sessions, or a complete future-module permission catalog.

Do not move security-principal ownership into Platform Operations or another business module.

Do not expose another module's JPA entity or repository.

Do not add an administrator account, password, MFA secret, recovery code, or reusable credential to source, migrations, tests, logs, documentation, CI artifacts, or AI context.

Business-module authorization call sites belong to the task that implements or hardens the applicable operation unless explicitly included in a focused IMP-013 work order.

## Database direction

Released Flyway migrations V1 through V4 are immutable.

TASK-0022 may allocate V5 if V5 remains the next free global migration version when implementation begins.

The first authorization schema should provide normalized relational integrity for roles, permissions, account-role membership, and role-permission membership. Enforce unique stable role identity, unique canonical role naming, unique permission authority keys, unique assignment pairs, and deliberate foreign-key behavior.

Do not seed a default account, administrator role assignment, credential, or customer value.

Later forward migrations must be used for later schema evolution.

## Security, privacy, and audit

Authorization must be enforced at application-service boundaries rather than relying only on Vaadin visibility.

Only stable non-secret identity and authority data may be retained in authenticated session state.

Raw passwords, hashes, MFA material, recovery material, and login secrets must never enter audit context, ordinary logs, diagnostics, fixtures committed to Git, or task documentation.

Administrative mutations introduced by later IMP-013 tasks must be auditable through the existing append-only audit foundation. TASK-0022 introduces no operator-facing administrative mutation API, so its primary security obligation is correct fail-closed authority derivation and schema integrity.

## Verification direction

Each TASK must include focused unit tests and, where persistence or MySQL behavior matters, real-MySQL integration verification through the existing Linux `mysql-it` profile.

Windows retains the ordinary full reactor build.

Authorization regressions must cover missing/disabled assignments, duplicate memberships, authority deduplication, authentication with no assigned authority, and successful authority propagation from persisted assignments.

Architecture tests must remain green and Identity & Access ownership must remain intact.

No test may depend on real customer data or reusable production credentials.

## Completion boundary

IMP-013 closes only after all required user, role, permission, assignment, secure provisioning, administrative authorization, audit, and applicable privileged-account MFA work has been integrated and post-merge verified.

After every focused TASK, perform a fresh-cycle review before allocating another TASK or advancing to IMP-014.
