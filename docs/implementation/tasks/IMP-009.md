## Objective and authority

Establish the smallest secure local Identity & Access foundation on which later HRIS modules and IMP-013 administrative access management can build.

Identity & Access remains the sole owner of security principals, credential/authentication state, and authorization according to D-089.

The implementation must establish:

- local username/password authentication with no internet dependency;
- adaptive one-way password hashing with an upgradeable stored format;
- persistent authentication/account security state;
- bounded authenticated sessions;
- failed-login protection and bounded temporary lockout;
- a stable authenticated principal using the existing public-ID convention;
- an application-facing authorization contract that later module application services can call;
- Vaadin/Spring Security integration with deny-by-default authenticated navigation.

Relevant frozen authority includes Master Plan §29, §65.1, D-065, D-089, D-106, D-108, D-109, D-111, D-112, D-123, D-130, D-132, D-148, and D-151.

No approved ADR applies.

Do not modify frozen planning sources.

## Scope and acceptance direction

Through focused work orders, IMP-009 may:

- add the required Spring Security dependencies without independently pinning versions already governed by the repository's dependency management;
- use a Spring Security-supported Argon2id implementation as the preferred password-hash target after verifying the exact API/dependency against the repository's current framework versions;
- store password hashes in a self-describing/versionable form so future hash upgrades do not require plaintext recovery;
- implement persistent account credential/security state through JPA/Hibernate and the global Flyway stream;
- normalize login identifiers deterministically and enforce uniqueness;
- track account enabled/disabled state, consecutive authentication failures, bounded temporary lock state, credential update metadata, and optimistic/concurrency state where required;
- use an injected `Clock` for lock expiry/security timestamps rather than host-default local time;
- apply the D-151 default 30-minute authenticated-session idle timeout through standard Spring Boot/servlet-session configuration;
- preserve normal Spring Security session-fixation, logout, and CSRF protections rather than replacing them with custom mechanisms;
- expose a narrow Identity & Access authorization/current-actor contract suitable for calls from future application-service boundaries;
- integrate Vaadin navigation security through the supported Vaadin/Spring Security mechanism;
- add focused unit, application-security, and real-MySQL authentication/migration tests;
- document password/session/lockout behavior, configuration, privacy boundaries, and outstanding production qualification.

The initial implementation must not seed a vendor-known or repository-known production account or password.

Password work-factor values are not considered production-qualified merely because framework defaults work. Calibration on supported hardware remains a production-security verification obligation.

## Boundaries

Do not implement:

- IMP-013's user/role/permission administration UI or full access-management lifecycle;
- business-module authorization call sites;
- a complete agency permission catalog;
- Worker/User lifecycle coupling;
- SSO, Active Directory, LDAP, OAuth login, or external identity-provider integration;
- full TOTP enrollment/recovery/challenge UI in the first TASK unless separately authorized;
- privileged-operation re-authentication flows unless separately authorized;
- password-reset/email/SMS recovery flows;
- HTTPS/certificate provisioning, which belongs to later production-hardening work;
- Redis or a distributed/session service;
- customer-specific security rules;
- a default administrator credential;
- changes to released Flyway V1 or V2.

Role and permission persistence/administration belongs to IMP-013. TASK-0012 may establish the authorization contract and synthetic/test authorities necessary to prove the boundary without pre-implementing that later item.

Authentication credentials, raw passwords, password hashes, MFA secrets, recovery material, and entered login secrets must never be written to audit context, ordinary logs, diagnostics, fixtures, Git history, or AI context.
