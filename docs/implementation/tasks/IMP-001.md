# IMP-001 — Maven Multi-Module Repository Skeleton

## Milestone

M0 — Engineering Foundation

## Priority

P0 — Blocking

## Status

COMPLETE (2026-09-29)

## Objective

Create the Maven multi-module repository skeleton and one deployable HRIS application according to the frozen Master Software Plan.

This task establishes the structural foundation for all later implementation work and must not implement business functionality that belongs to later IMP tasks.

Read before planning or implementation:

## Relevant Frozen Architecture

The approved repository architecture is a Maven multi-module modular monolith delivered as one deployable HRIS application.

Expected top-level direction:

```text
/
├── pom.xml
├── mvnw
├── mvnw.cmd
├── .mvn/
├── hris-app/
├── shared-kernel/
├── modules/
│   ├── platform-operations/
│   ├── identity-access/
│   ├── person-documents/
│   ├── client-management/
│   ├── recruitment/
│   ├── worker-master/
│   ├── client-deployment/
│   ├── scheduling/
│   ├── attendance/
│   ├── payroll/
│   ├── billing/
│   ├── compliance-rules/
│   └── reporting/
├── tools/
│   └── synthetic-data/
└── docs/
```

Important:

- `shared-kernel` must remain deliberately small.
- Business aggregates must not be moved into `shared-kernel` merely for convenience.
- One deployable application is the runtime baseline.
- The architecture is a modular monolith, not microservices.
- Module-boundary enforcement tests belong primarily to IMP-011.
- Synthetic-data implementation belongs to IMP-010.
- Authentication/authorization belongs to IMP-009.
- Audit implementation belongs to IMP-008.
- Flyway conventions belong to IMP-005.
- MySQL/Testcontainers belongs to IMP-004.
- CI belongs to IMP-003.
- Root `AGENTS.md` and full repository-governance structure belong to IMP-002.

## In Scope

IMP-001 may:

- inspect the current repository state;
- establish the root Maven parent/aggregator build;
- establish Maven Wrapper files;
- establish module directories and module POMs;
- create one deployable Spring Boot/Vaadin application module;
- create the minimum source/resource structure required for a valid build;
- centralize common Maven properties and dependency/plugin management where appropriate;
- configure module dependencies required only to establish the approved skeleton;
- create minimal placeholder code necessary to prove the application can compile/start;
- add minimal smoke/build tests required to prove the skeleton works;
- document the resulting module structure if needed for this task.

## Module Structure

The implementation should follow the frozen module map unless repository evidence reveals a material conflict requiring an ADR.

Expected Maven modules include:

- `hris-app`
- `shared-kernel`
- `modules/platform-operations`
- `modules/identity-access`
- `modules/person-documents`
- `modules/client-management`
- `modules/recruitment`
- `modules/worker-master`
- `modules/client-deployment`
- `modules/scheduling`
- `modules/attendance`
- `modules/payroll`
- `modules/billing`
- `modules/compliance-rules`
- `modules/reporting`
- `tools/synthetic-data`

A module may initially contain only the minimum structural code required for Maven compilation.

Do not introduce business implementations just to avoid an empty module.

## Dependency Direction

Avoid obvious dependency cycles.

The application module may compose/use business modules.

Business modules must not depend on `hris-app`.

`shared-kernel` may be used only for genuinely neutral primitives/shared technical contracts.

Exact executable architectural enforcement is deferred to IMP-011.

## Technology Versions

Do not guess current Java, Spring Boot, Vaadin, or Maven versions.

Use versions explicitly approved in the Master Software Plan when available.

If current-version verification is required before implementation, report it before editing rather than silently selecting versions.

Do not introduce preview/incubator language features unless explicitly approved.

- The packaged JAR launched on port `18080`. Logs showed Tomcat started on that port, Vaadin running in production mode, and `HrisApplication` reaching `Started`.
- `GET http://localhost:18080/` returned HTTP `200`, Content-Type `text/html;charset=utf-8`, and a Vaadin-generated bootstrap page rather than an error page. The static route text was not independently rendered in a browser because no browser was available to the computer-use tool. Browser rendering is not a separate mandatory acceptance criterion in this task; the startup and HTTP bootstrap evidence satisfies the application-start criterion.
