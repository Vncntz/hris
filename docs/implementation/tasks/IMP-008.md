## Objective and authority

Establish the common append-only audit foundation required by later HRIS modules without coupling audit to authentication, Vaadin, or any one business domain.

The frozen Master Software Plan §65.1 defines IMP-008 as P0 / M0 work item 8, “Implement append-only audit foundation,” depending on IMP-006.

D-065 requires a common append-only audit facility that records material actions including actor, time, action, target, reason, and context while complementing rather than replacing authoritative domain history.

D-109 permits genuinely neutral common audit contracts in the small `shared-kernel`. D-111 makes Spring Data JPA/Hibernate the default for normal persistence. D-112 requires short explicit transaction boundaries. D-123 requires technical instants to use UTC.

## Scope and acceptance direction

Provide a minimal neutral audit-recording contract in `shared-kernel` and its persistence implementation in `platform-operations`.

The shared contract must remain free of Spring, JPA, Hibernate, Jackson, Vaadin, authentication, and business-module dependencies.

The audit record must support:

- a stable public event identifier;
- UTC occurrence time;
- an explicit caller-supplied actor reference;
- action;
- target type;
- target reference;
- optional reason;
- optional privacy-minimized context.

The implementation generates the event identifier and timestamp through an injectable clock rather than host locale/time-zone defaults.

`platform-operations` owns persistence and exposes only append-oriented behavior to normal callers. Do not expose generic update/delete persistence operations as the application audit contract.

Use normal JPA/Hibernate persistence and the application's single Flyway migration stream. The next migration after current V1 is V2. V2 establishes the audit table and database-level protection against UPDATE and DELETE so accidental code paths cannot silently rewrite audit history.

The audit write participates in the caller's Spring transaction when one exists. Later domain tasks remain responsible for calling the audit facility at their own material command boundaries.

## Boundaries and dependencies

Do not implement:

- authentication or derive actors from Spring Security;
- users, roles, permissions, or sessions;
- generic AOP/entity-listener auditing of every persistence operation;
- Hibernate Envers;
- before/after snapshots of arbitrary entities;
- business-module audit call sites merely to demonstrate the facility;
- audit UI/search/report screens;
- retention/purge workflows;
- external logging/SIEM/telemetry;
- cryptographic log chaining unless separately required;
- transactional outbox or distributed messaging;
- customer-specific audit behavior.

Audit context must not become a dumping ground for passwords, secrets, documents, government identifiers, payroll details, or arbitrary serialized entity state.
