## Objective and authority

Establish the single installation-level Agency configuration/business root owned by Platform Operations. The frozen [Master Plan](../../planning/MASTER_SOFTWARE_PLAN.md) backlog assigns IMP-012 to M1 after IMP-006 through IMP-009. Decision D-081 requires one Agency per installation and database, without SaaS-style agency keys on every aggregate. D-109, D-110, D-111, D-112, D-132, D-147, D-148, and D-177 also govern module ownership, persistence, architecture verification, and scope. Use the [planning index](../../planning/INDEX.md) for targeted retrieval. No approved ADR changes this direction.

IMP-006 through IMP-009 and the M0 architecture foundation have reached verified post-merge CI. The `platform-operations` module currently owns the audit foundation but no Agency aggregate. The global Flyway stream currently ends at V3. The Identity & Access foundation exposes a `CurrentActor` authorization contract; IMP-013 owns later user/role/permission administration.

## Scope and completion direction

Through focused work orders, establish a durable Agency identity and minimal configuration needed by later M1 modules. Keep the root and its persistence inside `platform-operations`; expose intentional application/query contracts rather than another module's entity or repository. Enforce the one-Agency-per-installation invariant in both application behavior and the database, including concurrent creation. Use a stable public identifier separate from an internal relational key. Create Agency data only through an explicit, controlled setup path; do not seed a customer, vendor account, credential, or production value in a migration. Preserve appropriate audit evidence and authorization for changes. Use the existing global Flyway stream and real-MySQL verification for schema changes.

[TASK-0016](../../tasks/TASK-0016.md) is the initial root and persistence slice. It may close IMP-012 if it proves the singleton invariant, controlled creation and update, durable identity, module boundary, migration, audit and security behavior, and verified CI. Additional configuration fields should be added only when a later owning capability needs them.

## Boundaries

Do not introduce multi-agency tenancy or agency foreign keys across every aggregate. Do not implement IMP-013's role/permission administration, IMP-014's Client/Site model, licensing, health, backup/update operations, payroll or statutory configuration, broad UI workflows, or speculative settings catalogs. Do not change frozen planning sources or protected-main governance. No real customer data is required.
