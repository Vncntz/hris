## Objective and authority

Establish the single installation-level Agency configuration/business root owned by Platform Operations. The frozen [Master Plan](../../planning/MASTER_SOFTWARE_PLAN.md) backlog assigns IMP-012 to M1 after IMP-006 through IMP-009. Decision D-081 requires one Agency per installation and database, without SaaS-style agency keys on every aggregate. D-109, D-110, D-111, D-112, D-132, D-147, D-148, and D-177 also govern module ownership, persistence, architecture verification, and scope. Use the [planning index](../../planning/INDEX.md) for targeted retrieval. No approved ADR changes this direction.

IMP-006 through IMP-009 and the M0 architecture foundation have reached verified post-merge CI. Before TASK-0016, `platform-operations` owned the audit foundation but no Agency aggregate, and the global Flyway stream ended at V3. The Identity & Access foundation exposes a `CurrentActor` authorization contract; IMP-013 owns administrative authorization and current-actor wiring for Agency configuration.

## Scope and completion direction

Through focused work orders, establish a durable Agency identity and minimal configuration needed by later M1 modules. Keep the root and its persistence inside `platform-operations`; expose intentional application/query contracts rather than another module's entity or repository. Enforce the one-Agency-per-installation invariant in both application behavior and the database, including concurrent creation. Use a stable public identifier separate from an internal relational key. Create Agency data only through an explicit initialize command; do not seed a customer, vendor account, credential, or production value in a migration. Require an explicit actor public ID and preserve transactional audit evidence. IMP-013 adds the administrative authorization/current-actor adapter before an operator-facing setup path. Use the existing global Flyway stream and real-MySQL verification for schema changes.

[TASK-0016](../../tasks/TASK-0016.md) established the initial root and persistence slice. [TASK-0017](../../tasks/TASK-0017.md) hardened its migration regression. [TASK-0018](../../tasks/TASK-0018.md) addresses the observed intermittent initialization contention outcome with bounded fresh-transaction handling and deterministic plus real-MySQL verification. IMP-012 may close only after TASK-0018 is verified and a fresh-cycle acceptance review; do not infer IMP closure from TASK implementation alone. Additional configuration fields should be added only when a later owning capability needs them.

## Boundaries

Do not introduce multi-agency tenancy or agency foreign keys across every aggregate. Do not implement IMP-013's role/permission administration, IMP-014's Client/Site model, licensing, health, backup/update operations, payroll or statutory configuration, broad UI workflows, or speculative settings catalogs. Do not change frozen planning sources or protected-main governance. No real customer data is required.

## Fresh-cycle closure review (2026-10-01)

Reviewed the current `platform-operations` Agency service, entity, repository, V4 migration, module documentation, deterministic unit tests, and real-MySQL `AgencyConfigurationIT` after all three focused TASKs reached protected `main`.

- V4 creates an empty `agency_configuration` table; the fixed primary key and check constraint enforce one Agency per installation even for direct writes. The migration/revalidation test confirms no seed and one successful V4 history entry.
- The application exposes explicit initialize/current/update commands and an immutable projection. The public UUID is separate from the internal singleton key, survives update and context restart, and is never replaced by a sequential business ID. The caller supplies a non-null actor public ID and business time zone; no operator-facing mutation path or implicit administrator exists in this item.
- Successful initialization and material update append an Agency audit event in the same transaction. The real-MySQL rollback test removes Agency and audit together; duplicate and losing contention paths leave no success audit. The event omits name and zone.
- Update checks an expected version, uses JPA optimistic locking, preserves public identity and creation time, and rejects stale changes. An unchanged update does not create an audit event or version increment.
- TASK-0018's deterministic tests cover rollback-before-retry, bounded attempts, committed-winner detection, no-winner propagation, non-transient errors, and surrounding-transaction behavior. The real-MySQL simultaneous-initialization test confirms exactly one root, one clean duplicate outcome, and one success audit.
